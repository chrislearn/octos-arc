# v12 生成测试用例状态与执行规则

本规则按**测试用例**生效。一个 spec 文件或节点中有用例被排除，不会阻止同文件其他已确认有效的用例运行；排除的用例不产生通过证据，也不能驱动应用代码修复。

## 审核状态 `CaseStatus`

| 状态 | 含义 | 执行 |
| --- | --- | --- |
| `unreviewed` | 尚无有效的独立审核 | 跳过该用例，保留待审 |
| `needs_correction` | 该用例自己的动作或断言仍有错误 | 跳过；每场景最多一次审核修正 |
| `approved_behavior` | 用例自身有需求与断言见证，可带进一步改进建议 | 执行，可作为该用例的行为证据 |
| `approved_smoke_only` | 仅入口或可达性检查 | 不作为行为验收用例执行 |
| `invalid` | 应用一次修正后，独立复审仍确认该用例错误 | 隔离该用例，不再运行或修复应用来满足它 |
| `disputed` | 用例的正确性无法确认 | 隔离该用例，不运行或据此改应用 |
| `skipped_unreviewed` / `skipped_with_reason` / `unverified_gap` | 缺少可审核用例或可用前提 | 不运行，保留覆盖缺口 |

审核员必须把“已有足够证明、但还能增强”的用例判为 `approved_behavior`，将改进建议写入 `reason`。`needs_correction` 只用于用例自身错误或没有证明自身声明的结果。一次修正请求若失败、没有应用、或复审没有有效回复，不据此宣布用例无效；它继续保持待审或需修正。有效修正已经写入后，独立复审仍判 `needs_correction` 且给出具体原因，才转为 `invalid`。

## 运行后裁定 `TestDecisionState`

| 状态 | 条件 | 后续 |
| --- | --- | --- |
| `valid` | 已有证据表明测试本身可用 | 正常执行 |
| `invalid` | 两次独立审核对测试错误类别及需求/测试原文见证完全一致 | 隔离该用例，不改写后重跑 |
| `disputed` | 两次审核意见不一致，或证据仍不确定 | 隔离该用例，不据此修改应用代码 |

历史记录中的 `unresolved` 按 `disputed` 读取；新裁定只写上述三个状态。运行后裁定绑定需求、helper、测试标题和该用例自身内容：同文件其他用例变化不会让无效用例重新运行；该用例自身变化则使裁定失效并重新审核。生成前审核也绑定用例自身内容。

执行器只在临时 Playwright 副本中为被排除的标题注入 `test.skip`，原始 spec 保持不变。被排除的结果记为 `quarantined`，不计作通过。仍有有效用例的节点可以测量并修复其真实应用失败；若覆盖有缺口，节点最终仍保持未完全验证。没有任何有效用例时跳过该节点的本地用例执行，后续节点和最终系统检查继续。

已有逐用例审核记录的 v12 套件，在运行失败后不再自动改写测试并重跑；疑似测试错误进入上述双审核裁定。没有逐用例审核记录的旧套件保留既有的确定性修复兼容路径。
