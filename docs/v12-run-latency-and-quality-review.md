## 一、结论与证据等级

1. **本地慢主要发生在 REST 请求等待期间，而非本机编译或审核循环。** 代理账本中 16 次请求尝试的耗时合计 1795.2 秒；从第一条请求开始到最后一条结束共 1801.1 秒，请求之间的空档合计约 7.4 秒。代理计时包括请求链路、上游生成及本地设置的截止时间，不能只凭这组数据把慢完全归咎于模型服务端，也不能排除网关或网络。能确定的是，本机非请求处理不是主要墙钟耗时。
2. **我们的流程显著决定要等待多少次、等待多长。** 设计阶段 1066.0 秒，首波实现相关 653.8 秒；首波第一次回复耗时 445.7 秒，但因尝试覆盖未完整展示的构建配置而被保护机制拒绝。随后的完整引用重试耗时 149.9 秒并被本地截止时间中断，再拆成单节点请求。保护拒绝是正确的，额外长请求是可以优化的流程成本。
3. **成功且上报用量的请求表现出约 58 completion token/秒。** 6 次完整计量请求共输出 72,746 completion token，用时 1252.4 秒，约 58.1 token/秒；各次为 57.3–58.3。completion 包括 41,887 reasoning token。首波实现的 25,801 completion token 中 21,769 是 reasoning，约占 84%；可见正文约 4,032 token，445.7 秒相当于可见正文约 9 token/秒。不能将这种可见速度误读为本机卡住。
4. **线上两份项目能构建，但存在业务规则缺陷和审核缺口。** Sheet 的数值验证错误已用隔离数据目录复现；GitHub 的 PR 合并缺少冲突检查和双父提交，且多集合写入不能保证原子性。两份产物中的节点测试准入均为 `waiting_for_review`，不能把测试文件数量当作通过数量。

总计 16 次请求尝试，3 次 502，7 次 HTTP 200 但 `stream_guard=turn_deadline` 且无供应商用量，因此**13 个 HTTP 200 不等于 13 个有效模型结果**。已上报输入 88,719 token，其中缓存命中 12,672，比例 14.3%；另外 10 次尝试缺少供应商用量，不能按零成本处理。代理没有记录可用于准确分解首 token 延迟、持续输出速率、网关排队和模型推理的完整时间序列。因此 58 token/秒是端到端观测值，不是对提供商内部吞吐的断言。502 的错误分别为一次连接拒绝、两次读取超时，属于请求链路失败；本日志不足以定位到提供商、网关或本地代理中的哪一段。

复查 `arc/llm_proxy.py` 的请求路径，未发现逐 token 的本地限速或人为等待；唯一显式 `sleep(1)` 用于失败后的第二次尝试。流守护线程的短周期 `wait(0.2)` 是等待完成/截止的轮询，不是阻塞上游输出。因此稳定的约 58 token/秒不应归因于本地代理主动节流，但仍不能据此分清远端模型、网关及网络的贡献。

设计请求与首波实现的已计量输出合计 72,746 token，正好解释 1252 秒的大部分等待：在约 58 token/秒下，仅这些输出就需约 21 分钟。提示词体积也大：首次首波约 80,175 字符，完整引用重试约 85,388 字符，拆成单节点后仍约 80,404 字符。输入体积可能增加排队或首 token 延迟，但目前没有该细分计时，不能量化。

**责任归因应分两层：** 单个完整请求约 58 token/秒的端到端输出速度和三次请求链路故障，不是本机代码在逐 token 限速；但我们的设计和波次编排选择了数万 token 的输出、在 445.7 秒的回复后因缺少源文件上下文整次拒绝、再以 149.9 秒进行重试，并在预算尾部派发 75.4 秒的短请求。这些都是我们能够改进的放大因素。不能把整段 30 分钟都称为“模型太慢”，也不能说仅凭优化本机循环就能解决。

## 三、流程造成的放大效应

### 设计阶段

当前 `arc/main.py` 的应用设计先做整树合同；归属不完整时做一次紧凑重试，再按类别恢复并做最多一次修正。这些请求依赖前一结果，不能直接并发。本次 6 个设计回合合计约 1066 秒，约占 1804 秒总预算的 59%。恢复将缺少显式产物归属的叶子降至 1/24，但 `design_readiness` 仍记录 20 个节点存在未解决的语义/共享合同阻塞，不能把“有 owner”视作“设计已审核正确”。

REQ-2 的模型回复含 `shared/request.js`，不符合合同要求的 `frontend/` 或 `backend/` 路径；安全校验正确拒绝了该字段。REQ-3 的 239 秒读取超时和 REQ-2 的 78.5 秒失败不应被计为生成进度。改进目标应是减少对完整 JSON 的反复再生成：先确定性分配文件所有者和合法路径，再让模型补充小而独立的业务合同；仅对出错字段作有界修复，并保留原文需求的可追溯引用。不能用自动猜测任意路径或静默删除需求来换速度。

### 首波实现与文件保护

第一次波次请求覆盖两个节点，耗时 445.7 秒。模型同时改写 `frontend/build.mjs` 和 `frontend/vite.config.mjs`，但提示词没有展示这两个既有文件的完整内容，写入保护拒绝了回复。随后重试把两文件完整加入上下文，提示词增至 85,388 字符，在 149.9 秒后被截止时间中断。拆成一个节点后才在 58.2 秒写入 5 个文件。**不应放宽保护**；更安全的改进是将通用构建文件默认列为不可修改，只有经设计阶段证实必要时才完整引用并允许修改。若模型仍提出额外文件，先返回允许路径错误，再做一次小范围修正。需要保留回滚和源文件哈希检查。

### 时间预算与状态

波次退出后，节点流程依次以 74、29、12、5、2、1、0 秒预算启动多个实现请求；它们均未形成可接受结果。`time_up()` 只阻止预算严格耗尽时的节点，而 0.x 秒剩余仍可进入，随后产生本地截断请求。应在派发前要求最小可完成时间，并预留构建、启动和审核时间；不足时把节点记为 `pending_budget` 或等价待处理状态，而不是发起几秒的无效请求或将其与真实代码失败混在一起。此次本地最终 24 个叶子仅 1 个 `IMPLEMENTED`，其余失败状态主要受预算截断影响，不能推断为模型无法实现这些需求。
