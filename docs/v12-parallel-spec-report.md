# v12: 并行生成测试 spec 的隔离与提交方案

## 调查范围与结论

以运行 `64f249afb2a8` 的需求树和当前 `arc` 实现为依据。该运行有 5 个一级类别、24 个叶子需求、100 个原始场景；场景去重后有 58 个目标。需求树有 49 条显式叶子依赖，其中 30 条跨一级类别，且 REQ-2 与 REQ-5 存在双向类别关联。因此类别不是独立业务分区；但在完整需求树、应用设计、fixture 与 helper 版本固定后，各叶子的**文本生成和只读审核**可以并行。

`derived-tests/<node_id>.spec.ts` 按叶子分文件；不同叶子的最终 spec 无同文件写冲突。同一叶子的多个场景采用读改写追加，必须单写者提交。真正共享的是 `review/obligations.json`、`review/plan.json`、`review/cases.json`、批次号、运行预算、模型代理可变字段和整棵测试目录的保护快照。现有 `prepare_derived_spec_batch()` 不可直接在线程中并发调用。

## 安全边界

| 阶段 | 并行单元 | 必须串行的步骤 | 提交所有者 |
| --- | --- | --- | --- |
| 需求义务 | 不相交的叶子批次 | 同批次提取后独立复核 | 主协调器合并义务及状态 |
| 场景提案 | 不相交的场景批次，优先保持同叶子 | 失败提案后的定向重试 | 主协调器校验并追加叶子 spec，更新 plan |
| 独立用例审核 | 已固定文件哈希的用例批次 | 某叶子修正后的重新审核 | 主协调器合并 cases |
| 接纳与执行 | 无 | 全局快照、接纳、运行测试及应用修复 | 主协调器 |

模型工作者仅接收基于当前需求树、设计和 fixture 构造的不可变提示词，在独立的代理、Octos 进程、配置目录、数据目录和空工作目录内运行，不能写正式产物。任务完成后按派发序号合并。需求树和设计在该批次内由主线程保持固定；审核结果提交前再核对 helper、fixture 与对应叶子 spec 的输入哈希。失配结果留为未审核，等待后续批次重试，不能沿用审核通过状态。正式产物及全局快照只有主协调器可以写。

## 预算与缓存

默认并发窗口为 2，可通过 `OCTOS_ARC_SPEC_PARALLEL_WORKERS` 调整或设为 1 退回串行。派发前统一预留请求次数、时间和保守 token 上限；每个工作者的代理设置相应硬限，完成后把实际使用量合并回运行账本。并发中的未完成请求也占用预留额度，避免各工作者都误以为有完整全局预算。区分“模型耗时累计值”和“阶段墙钟时间”。

缓存的关键是上游请求字节前缀，而非是否使用同一个本地代理。工作者保持相同模型、system prompt、推理参数与固定顺序的共享来源上下文；不得在共同前缀前插入时间或工作者 ID。先让一个请求预热，再打开有界并发。通过实际 `prompt_cache_hit_tokens`、总 token、墙钟耗时和审核通过率共同评估。

## 实施与验收

1. 加入独立模型请求工作者及有界请求调度；不在后台线程运行可变的主 `Flow`。
2. 并行化不同批次的义务首轮提取、场景首轮提案和用例首轮审核。各自的独立复核、格式重试、纠错和复审保留原有依赖顺序。主线程按原序校验并提交。
3. 验证不同叶子无正式文件并发写入、共享账本稳定、预算耗尽不越额派发、过期审核不能被信任，以及并发关闭时保持原行为。

## v12 实施与复审记录

- `spec_parallel.py` 提供预热后最多 2 个并发请求的有界队列；工作者有私有代理、Octos 数据/配置/运行目录，且禁用工具。工作者只返回文本和用量记录。
- `main.py` 在主线程预留请求编号及 token 额度，按原序合并结果和用量；主代理的全局 token/审核轮次检查同时计入工作者在途预留，避免串行复核与并行任务争用同一额度。场景生成的墙钟额度按实际阶段时间计算，不把重叠的模型耗时相加。
- `obligation_planning.py` 并行首轮提取、串行执行每批后续独立复核；用例审核在接受结果前核对 spec、helper 和 fixture 哈希。
- `pack.sh` 已包含新模块。测试覆盖请求重叠、顺序提交、早停后的用量归账、工作目录隔离、文件变化后的审核失效和独立打包导入。
- 线上真实模型的缓存命中率与提速倍数尚无 v12 实测，部署后应对比 `prompt_cache_hit_tokens`、完整审核率和阶段墙钟时间。

## 场景提案的两次上限

对同一个叶子节点，场景提案模型请求合计最多两次，首轮、不同场景批次和规则校验后的定向修正共用这个额度。多个场景先尽量合并到同节点的批次；如果该节点已安排两个首轮批次，第一批的拒绝项不再另开修正请求，保留缺口状态。并行派发时在请求提交前计数，防止在途请求越过上限。简单节点通常是一次提案，只有校验不通过才用第二次修正。

需求义务的独立复核和生成用例后的行为审核是不同的准入检查，不计入上述提案额度。行为审核按用例及文件版本记录；修正文件后必须重新审核，未获认可的用例不能作为通过证据。这个区分避免为了节省提案次数而把未审核的测试误判为通过。

本报告区分代码结构判断与线上测量：预计缩短等待时间，但具体提速倍数须由部署后的相同规模运行验证。
