## 生成失败的根因

### 共享坐标契约不一致

[`columnName`](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/original/template/backend/lib/formula.js:13) 接收 0 起始索引，`colIndexNum` 返回 1 起始列号。`shiftRefs` 和 [`adjustFormula`](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/original/template/backend/routes/workbooks.js:447) 却直接把后者结果传回前者。这样不只是复制横向偏一列，插行、排序移动公式、绝对列引用也会受影响。

另外，向 A 列右侧插列时，真正插入位置是 B；路由用原列 `col` 调整引用，应使用计算后的 `target`。这会错误移动本来不受影响的 A 列引用。

建议统一坐标表示，并对每种转换明确输入输出。用 `A → index → A`、`Z → AA`、只插行不改列、未受影响引用保持不变等不变量检查共享函数，再执行浏览器场景。现在多个功能分别拼接公式重写，错误会跨节点传播。

### 修复调度把测试超时上限当成预期耗时

基线中 **7 次** `node_repair_window` 决定 `keep_measured_state`。已有数十分钟可用，却因预留测量时间过大而放弃本节点的业务修复。

| 节点 | 可用秒数 | 预留测量秒数 |
| --- | ---: | ---: |
| 普通复制剪切 | 2529 | 2629 |
| 公式 | 2614 | 4025 |
| 公式复制 | 2645 | 4455 |
| 筛选 | 2511 | 4644 |
| 数据验证 | 1973 | 6286 |
| 工作表切换 | 2763 | 4449 |
| 排序 | 2556 | 4665 |

后续透视表日志又出现一次：1919 秒可用，预留 6631 秒，继续推迟修复。

分析时的本地 `node_measurement_window` 仅复用整个测试集合、case 范围、workers、运行配置等完全相同的历史计时。每次加入新 spec，联合范围往往没有完全匹配的历史样本，于是回退到 [`measurement_seconds`](/home/chris/Works/octos-arc/arc/flow_policy.py:69)：启动常数加上每例超时上限乘以 1.2。

公式复制节点能精确对上这个计算：联合 59 例、每例 60 秒、单 worker，估算 `60 + 1.2 × 59 × 60 = 4308` 秒；再加目标测量预留约 147 秒，得到日志中的 4455 秒。相比之下，附近 52 例回归的实际执行约 137 秒，7 例目标约 93 秒。3000 秒的节点预算容不下估算值，后续复杂节点因此几乎必然被推迟到全量修复阶段。

建议优先修这里：组合复用兼容的 spec 或 case 实测耗时，分别保留预计值与最坏上限；给未知范围设置有界估算；允许一次聚焦修复并为完整回归保留截止时间。测试覆盖和通过标准应保持，不应通过删用例解决调度问题。

### 对共享文件的反复修改缺少接口约束

codegen 应用事件中，`backend/routes/workbooks.js` 被修改 19 轮，`Editor.jsx` 16 轮，`Grid.jsx` 4 轮；这些数字尚不包括 structured tools 的全部写入。典型问题包括 Home 留下未导入的 Link、列操作使用不存在的函数名、Grid 遗漏 `onCommitDropdown`、筛选逻辑插入错误作用域。粘贴与选择修复各出现 React 310 运行错误，浏览器 trace 分别指向 hook 调用。

编辑器中还存在语义不一致：[`commitEditing`](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/original/template/frontend/src/pages/Editor.jsx:219) 仅当字符串改变时写入；CSV 导入的 `=A2*2` 文本即使用户明确按 Enter 提交也被忽略，而公式栏提交会重新解释。这是操作语义与字符串相等判断混淆。

建议把坐标、公式变换、工作表结构变化与附属状态迁移集中到清晰的接口；让 grid、公式栏、blur、Enter 共用提交语义。对 hook 顺序、未定义引用、组件 props 和外部组件导出运行廉价静态检查，再启动浏览器验收。

### 上下文与输出协议增加成本

基线有两次 incomplete blocks、一次编辑锚点匹配失败，以及一次输出触达 16384 completion tokens 上限。验证、排序和透视表节点因 `required_wave_sources_exceed_budget` 转入工具模式。验证实现阶段用了 31 次请求、约 122 万 prompt tokens，之后仅修漏接属性又用了 5 次请求、约 18.7 万 prompt tokens。

这说明共享文件膨胀和上下文选择值得优化，但不足以证明某个模型整体不适合任务。基线记录的 149 次完成请求全部 HTTP 200，没有证据把主要问题归因于模型服务网络失败。

### 后续节点继续暴露跨对象状态迁移问题

第二份快照的[失败明细](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/late-failures.json)和源码说明：

- **透视表源范围未随插行变化。** [`shiftPivotSource`](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/late-snapshot/template/backend/routes/workbooks.js:281) 被传入发生结构变化的源 worksheet，但 `pivotState` 存在另一个结果 worksheet 上。因此源范围实际上没有扩大，刷新漏掉移到原范围之外的记录；East 合计应为 40，实际为 10。
- **空分组直接被丢弃。** [`firstAppearance`](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/late-snapshot/template/backend/routes/workbooks.js:247) 使用 `filter(v => v !== '')`，SUM、COUNT、AVERAGE 的三个空列分组用例因此失败。相同函数也用于行分组，空行分组值得补测。
- **把字段名称当作字段身份。** `colOf` 只使用 `headers.indexOf(name)`。删除原 Sales 列后，旁边同名列移入，程序把它当作原字段继续计算，未保留旧结果并提示重新选字段。
- **非活动表删除后没有切到邻居。** [`delete worksheet`](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/late-snapshot/template/backend/routes/workbooks.js:437) 仅在目标恰好是活动表时更新 `lastActiveWorksheet`。这里需求明确要求成功删除后激活相邻表，两个失败测试有依据。

这些问题说明仅移动 cells 不足以实现结构修改。应同时迁移指向该源表的公式、筛选、验证与透视表元数据，并维护字段身份和删除失效状态。

## derived tests 中已确认的问题

### 排序测试没有建立表头前置条件

[`REQ-5-1-1.spec.ts:55`](/home/chris/Works/octos-arc/arc/derived-tests/hackathon--sheet/REQ-5-1-1.spec.ts:55) 起的四个新增用例，断言首行不参与排序，却没有勾选 `Data has header row`。需求只规定“声明为表头时不参与排序”，没有要求默认选中。

在测试副本中显式勾选，并在重开对话框时重新声明，原始程序的排序结果从 **5/10 到 7/10**。两个日期用例仍失败，但此时才准确暴露程序将英文月份日期按文本排序的缺陷。另一个失败是共享公式引用转换。不能把原来的五个失败都归为排序实现错误。

### 故障注入学到了另一种业务请求

[`learnWrite`](/home/chris/Works/octos-arc/arc/derived-tests/hackathon--sheet/helpers.ts:213) 抓取操作期间第一个成功 HTTP 写请求；`matchesWrite` 又要求 method 和 URL 完全匹配。两处用例因此实际没有注入失败：

| 用例 | 学到的请求 | 真正执行的请求 | 云端结果 |
| --- | --- | --- | --- |
| 删除验证规则失败，spec 第 237 行 | 创建规则的 PUT validation | DELETE validation | 正常 200，注入次数为 0 |
| 首次保存规则失败，第 259 行 | 编辑单元格的 PATCH cells | PUT validation | 正常 200，注入次数为 0 |

应从同一种业务操作学习请求，并记录目标请求被截获及返回 500 的证据。还要防止选择持久化等后台写入抢先被捕获。无法注入时属于测试适配器问题，不能给产品下“未回滚”的结论，也不应静默跳过。

首次规则保存用例还有第二个问题：刷新后重开新规则对话框，直接填写 Minimum，未重新选择 Number range。需求没有指定新规则的默认类型。修正同类请求学习和这一前置条件后，原始程序该例 **1/1 通过**。

修正删除规则的注入后，测试会继续走到已有的错误文案缺陷而失败；因此修复注入不等于证明整条删除失败流程完全正确。测试副本中的验证总数仍为 24/31，失败位置发生了变化。

### 普通复制用例在执行目标动作前失败

[`REQ-3-2-1.spec.ts:8`](/home/chris/Works/octos-arc/arc/derived-tests/hackathon--sheet/REQ-3-2-1.spec.ts:8) 先向 J10 写入外围哨兵值，但该空白表只有 A 到 H 列。trace 表明测试卡在这一步，尚未执行复制。

改用同样位于全部操作范围之外的 H10，原始程序 **4/4 通过**。建议哨兵使用已有可访问单元格，或先通过 UI 建立所需列。空白表扩展能力应单独评估；不能把这个结果归因于复制机制失效。

### 需要明确或放宽的测试契约

- 部分保存失败用例强制错误元素具有 `role=alert`，需求只要求显示错误。此处是静态审查发现的额外约束，当前程序使用 alert，未因此失败。应按需求验证可见错误，除非产品契约明确规定角色。
- Clear selection 两例要求从已保存条件切换为空值集合。该交互意图合理，但[需求描述](/home/chris/Works/octos-arc/arc/derived-tests/hackathon--sheet/requirements.yaml:2434)仅分别说明值筛选与条件筛选，没有写清同一列二者的优先级与切换。建议先明确规则，再把对应转换作为强制门禁。
- `=#REF!` 的精确表达式，以及数值错误中 `between` 与特殊场景 `from` 的区别，需求已有明确文字，不能为迁就当前程序而放宽。若要统一文案，应同时修改源需求和测试。

### 透视表特殊键用例混入未规定的空组合显示

后续快照中，`constructor`、`toString`、`__proto__` 三例均在 B3 的 `0` 与空白差异上失败。程序用 Set 与数组分组，报告没有显示这些键导致聚合对象冲突。需求只明确规定 **COUNT** 的空组合显示 0，未规定 **SUM** 的空组合必须显示 0；同一 spec 较早的 column SUM 用例也特意不约束无记录的组合。

这三例应保留特殊键对应的真实聚合值、全部总计和源数据不变断言，把 SUM 空组合显示策略单独明确。只移除 B3 空组合的额外断言、不改后续快照的产品源码，本地 **3/3 通过**。因此不能根据标题把三个失败直接归类成原型键漏洞。诊断测试副本位于 [pivot-special-keys.spec.ts](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/late-test-controls/pivot-special-keys.spec.ts)，[执行结果](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/control-pivot-special-keys/summary.json)。

## 覆盖不足与新增探针

新增两个 UI 探针，原始程序 **0/2**，对应逻辑修正后的副本 **2/2**。代码见 [candidate-boundaries.spec.ts](/home/chris/Works/octos-arc/arc/diagnostics/b0c8de00a1c6-20261002/probes/candidate-boundaries.spec.ts)。

1. **数值相等但文本不同的稳定排序。** 输入 `2、02、2.0`，数值键相等，应保留三条记录原顺序。当前比较器在数值差为零后退回字符串比较，把 `02` 移到前面。现有同文本键的稳定排序用例不能发现它。相同日期的不同等价写法也应覆盖。
2. **插入点之外的引用不应变化。** A 列右插一列后，`=A1+B1` 应变为 `=A1+C1`。现有插右用例只验证 B 变 C，没有验证 A 保持不动，漏掉传入 `col` 而非 `target` 的边界错误。

建议下一批补充：

- 公式复制的混合绝对引用 `$A1`、`A$1`，以及 Z 到 AA 的列边界；分别覆盖上下、左右偏移与不受影响轴。已有 `$A$1` 测试应保留。
- 透视表空行分组和空列分组分别覆盖；将特殊键安全、空组合呈现、字段删除后的身份变化拆成独立断言，便于定位。
- 生命周期操作的有效输入在写入失败后无半成品、可重试。当前 coverage ledger 已承认需要 harness。
- 真实存储失败与进程重启后的持久化。浏览器拦截 HTTP 500 验证了客户端失败路径，并未证明服务端部分写入会回滚。
- 并发选择与保存响应交错后的最终状态。已有失焦、保存失败、跨表选择用例，应扩展关键时序，而不是重复正常点击路径。
- 对有意损坏的实现验证测试灵敏度：关闭注入匹配、让数值相等时按字符串排序、让全部引用统一偏一列等。通过测试必须建立在确实触达目标行为的证据上。

## 建议处理顺序

1. **先修测量时间估算与故障注入适配。** 前者让真实缺陷得到修复机会，后者让修复目标可信。
2. **统一坐标、引用变换和提交语义。** 本地同范围 12 例净改善证明这是收益最明确的共同根因。
3. **修测试前置条件并加入两个已复现的新边界。** 同时明确筛选模式切换规则，保留现有业务断言。
4. **修验证规则查找、非 ISO 日期、筛选区域迁移等独立缺陷。** 将共享函数的快速检查放在昂贵 UI 回归之前。
5. **再扩大存储故障、重启与并发时序覆盖。** 完整 187 例与云端 Stage 3 仍需对最终源码单独验证，不能用本报告的局部实验替代。
