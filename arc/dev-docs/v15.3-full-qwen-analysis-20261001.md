## 上下文与预算

初始请求 GitHub 74400 字符、工作表 59713 字符，显著低于 196608 上限。实际首请求含新草稿对象、commit 内层条件与选区一致性规则。当前证据不支持把注册、夹具、权限数据形状和未接线事件归咎于总上下文不足。筛选节点的正常 stop 响应却有未结束的巨型 EDIT，原子拒绝与一次补全重试正常生效；重试重新组装提示遗漏刚读过且未变化的 backend 路由，模型又花 97.935 秒请求相同文件。补全最后仅写入 backend 路由，前端 Data 控件没有实现，原始五个筛选用例均在该共同前置步骤超时，0/5；不能把这些失败解释为五种筛选算法已被证明错误。这是恢复轮次上下文闭包丢失，需保留路径及版本，而不是统一缩短读取预算。

GitHub 第 13 个节点首次因 `preservation_contracts_need_tool_reads` 切工具模式。源码核查：保留契约有独立 24000 字符上限，在计算总 prompt 空间前即可能溢出；因此单独放大 196608 总额度不能解除此原因。这次保守切换不等于行为失败，但应记录各分区、遗漏 owner 和实际工具交付结果。后续提示增大后应另行统计完整源文件是否被遗漏或截取。优先补齐当前功能所需的 API 路由、数据模型、消费者与冻结夹具投影，再决定是否放大总预算。焦点工具提示中预置整文件源码的 32768 字符上限与总 prompt 上限独立，并不等于后续所有 read_file 结果仅能保留 32768 字符；放大后者不会自动修好前者。reasoning token 属于 completion token，缓存 token 属于 prompt token，不重复加总。网关没有提供可核实的金额，本实验按 token、请求数与时长记录成本。

数据校验节点另有**明确的容量反例**：初次 implementation_context 记录已引用 Editor、未引用 backend/routes/workbooks.js；收到 NEEDS_CONTEXT 后重组提示提升后端路由及其库，却删除了先前已引用的 Editor。重组提示 187858 字符，再加入未变化 Editor 至少 228157 字符（不含新增分隔符），超过 196608，总体没有源码写入。初始目标 0/7，修复随后因 required_wave_sources_exceed_budget 切工具模式。此处放大必须源闭包容量有依据，但应按需扩展、记录丢失路径并保持版本，而不能把所有失败归为上下文不足。[证据](../diagnostics/v153-full-qwen-20261001/sheet/validation-context-closure-budget.json)。
