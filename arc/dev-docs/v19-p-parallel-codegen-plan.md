# 并行代码生成方案（复核版）

## 目标与当前判断

目标是缩短从应用设计完成到各需求源码落盘，以及整次任务结束的墙钟时间，同时保持构建、验收结果和总成本可控。先测量，再对能明确分配文件所有权的独立功能组试验并行生成；没有至少两个合格组时，继续使用现有顺序 wave。

测试来源先固定：有官方 Playwright spec 就直接使用；没有时调用 `octos arc generate-test-suite`，命令未提供可信且完整的套件就停止。Python 端原有的 AI 测试规划、后台生成和无测试代码生成路径不再参与运行。代码生成仍由 `whole_app_waves()` 顺序处理 wave，或由 `implement_sequential()` 顺序处理节点。每个 wave 会读前一轮生成的源码，可能改共享路由、入口和清单，还会在落盘后做源码检查与必要回滚。首版只考虑可分组的 wave codegen 路径，不改变单次整应用生成、工具模式或节点流程。

## 对上一版的复核

| 上一版假设 | 当前代码事实 | 修订 |
| --- | --- | --- |
| 预测写集可作为并行边界 | `whole_app_wave_targets()` 排的是提示词可见源码，还主动加入共享 composition 文件；`phase_plan` 的 artifact owner 也主要用于上下文协调。 | 规划器另建显式允许写入路径/前缀。写集未知、共享或有重叠时不并行。 |
| “依赖已满足”才能生成 | `pending_dependencies()` 和 `admit_node()` 把未通过测试当风险证据，仍允许源码生成；环依赖可共同构建。 | 只因源码/接口输入未稳定而等待；不拿测试 verdict 当生成闸门。环依赖合组或串行。 |
| 可直接复用旧规格并行器 | `OrderedSpecRequests.ordered()` 属于已退出运行路径的 Python 测试生成器，先只发一个请求，之后按提交顺序等待。 | 只借鉴隔离、预算预留与记账原则，新建代码生成的完成队列；不复活测试生成流程。 |

| 合并已经是原子的 | 当前有写前检查，也有写后 `generation_batch_check()` 与快照回滚；没有现成的并发候选事务。 | 在临时快照准备候选，主线程比对版本、检查并应用；失败沿用回滚和串行修复。 |
| 生成阶段 p50 降 25% 即可默认开启 | 该指标漏掉集成、修复、验收时间，阈值也未经基线校准。 | 同时衡量整次运行 p50/p90、成功率和每次成功运行的 token/成本，试验后确定默认门槛。 |
| 总负责 agent 必须一直参与每个动作 | 当前只有一次应用设计及顺序 `Flow`，没有现成的常驻总负责模型会话。频繁调用总负责模型可能成为新瓶颈。 | 将其定义为决策角色：常规调度与权限检查由确定性 `Flow` 执行；只在共享底座、模糊所有权、共享修改请求时调用总负责 agent。 |
| 子 agent 可一边交局部补丁一边请求共享修改 | 当前 FILE/EDIT/`NEEDS_CONTEXT` 协议没有这种混合结果；局部补丁可能依赖尚未获批的共享接口。 | 首版一次回复只接受“权限内候选”或“共享修改请求”之一；请求解决后再生成受影响任务。 |
| 所有越权块都能转成共享请求 | 越权目标还可能是测试、数据或工作区外路径。 | 只有事先声明的共享路径可形成请求；其他越权路径直接拒绝并记录。 |

## 行业做法与本项目的取舍

- Codex 用独立任务与 Git worktree 隔离并行修改，保留可审查的 diff；这解决的是并行工作空间与合并边界，不表示同一应用的任意代码块可以无条件并行。[Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)
- Claude Code 的 subagent 适合有界任务与上下文隔离；agent teams 用共享任务表、依赖和消息协调独立任务。官方明确提示：同文件编辑、强顺序依赖会抵消并行收益，任务要有不同的文件所有权。[Claude agent teams](https://code.claude.com/docs/en/agent-teams)、[Claude subagents](https://code.claude.com/docs/en/sub-agents)
- Cursor 的后台代理运行在隔离环境与独立分支，异步提交成果供检查。[Cursor background agents](https://docs.cursor.com/background-agent)

本项目可复用上述共同模式：**先定共享契约，隔离并发生成，单线程验证与集成，遇冲突退回顺序生成**。这些产品的工作区隔离是架构参照，不能直接证明本项目内部并行一定提速。

## 总负责 agent 与写入协议

设一个总负责 agent 负责拆分需求、确定依赖与接口、指定每组的文件所有权，并对共享文件拥有唯一写权限。它是**决策角色**，不必是持续占用模型请求的独立会话：已有应用设计可作为第一次输入，规则明确的调度由 `Flow` 执行，模糊归属和共享改动再交给总负责 agent 判断。`Flow` 主流程强制执行边界、记账、校验和落盘；不能只靠提示词要求子 agent 自觉遵守。

1. **先建立共享底座。** 总负责 agent 先复用现有通用模板、清单和应用源码，只补充必要的路由注册方式、公共类型/数据形状与模块导出约定，并发布共享文件的版本。先固定接口和最小骨架，不重写已有入口或预先实现所有业务细节，避免把并行收益耗在一个庞大的串行前置任务上。
2. **发带权限的任务包。** 每个子 agent 收到需求 ID、依赖、允许写入路径或新文件前缀、只读共享路径、接口契约、基线版本与完成标准。所有未列入允许范围的路径均不可写；两个并发任务包的可写范围不能重叠。
3. **共享修改走请求。** 子 agent 发现必须修改已声明的共享文件时，本轮只返回 `SharedChangeRequest`：目标路径、原因、所需接口/行为、建议改动、依赖它的需求 ID 和基线版本。本轮不同时提交局部 FILE/EDIT；任务进入 `blocked_on_shared`，直到请求有决定。
4. **总负责 agent 统一集成。** 总负责 agent 可采纳、改写或驳回请求；采纳时由主流程单线程修改共享文件并发布新版本。请求按一批 worker 的边界汇总处理，避免每次请求都打断其他在途任务。受影响候选按读入源码版本检查，过期则重建提示词或串行回退。

子 agent 的文件权限由候选解析后的路径检查和应用边界强制执行。路径必须规范化并验证仍位于授权源码目录内；符号链接、路径穿越、测试及数据目录不得借“共享请求”绕过边界。即使模型返回了已声明共享路径的 FILE/EDIT 块，也不能直接落盘；首版将这种混合/越权响应拒绝并提示它单独提交请求，不自动把代码块当作已获批修改。

每批任务固定一个共享版本 `epoch`。任务包记录模型实际看到的完整源码文件哈希及共享接口版本；总负责 agent 在批次边界集中处理请求并发布下一版。首版采用批次屏障：收齐回复或超时结算后，先处理共享请求，再校验并应用局部候选，避免先落盘的候选被同批共享修改悄悄破坏。旧候选只有在其所读文件和接口版本仍有效时才能应用。保守版本检查若导致大量废弃回复，说明拆分边界不合适，应降低并发或退回顺序生成，不能跳过校验。

## 实施顺序

### 0. 固定基线并量化耗时

在同一提交、输入任务、模型路由、预算、环境和测试来源上记录串行基线。现有 `llm-usage.jsonl`、`flow-metrics.jsonl` 与 `analyze-run.py` 可作起点，但历史数据不足以证明并行收益。补齐设计结束、首个可构建源码、全部源码落盘和整次任务结束的时间点，并拆出 LLM 等待、回复重试、应用、源码检查、修复与验收耗时。对代表任务计算独立组数和关键路径；若耗时主要来自单次大回复、共享文件修复或验收，就优先优化那些环节。

试验前估算：并行墙钟时间约为“共享底座 + 最慢子任务 + 集成 + 废弃回复重做”，串行墙钟时间约为各组耗时之和。若独立组数不足，或共享/重做成本已接近可节省的模型等待时间，停止并行路线的实现，优先改善现有 wave 的提示词与修复效率。

### 1. 规划可并行的工作组

基于需求依赖图、应用设计和 `phase_plan` 构造有限大小的候选组。`phase_plan` 只提供候选边界，不自动授予写权限。总负责 agent 先建立最小共享底座，再由规划器产出任务包：需求 ID、稳定接口、允许新建的路径/前缀、可修改的已有文件、只读共享路径、输入源码版本和预计输出预算。接口需要写明模块导出、路由注册、共享数据形状；仅有抽象设计描述而没有可核对契约时不放行。若两组需要同一文件，合成一个组或回到现有 wave；未知路径、接口不清晰或无法合组的环依赖也回退。测试通过与否只影响证据，不阻止源码生成。

### 2. 受限并发生成候选补丁

在功能开关下只试验无工具的 wave codegen，默认走串行，先开 2 个 worker。每个 worker 使用冻结源码快照和私有代理/内核，一轮只返回权限内 FILE/EDIT 候选或 `SharedChangeRequest`，以及用量、耗时和错误；不写共享源码、测试或 `Flow` 账本。借鉴旧 `spec_parallel.py` 的预算预留与用量合并原则，但新建按完成顺序收件的调度器；遵守全局 token、请求、时间和供应商并发上限。首版不在 worker 内做 `NEEDS_CONTEXT` 循环、结构化工具编辑或回复后的自动修复；遇到这些情况就记录原因并串行回退。超时、取消、限流后仍须结算每个已发请求。

### 3. 单线程集成与冲突回退

先把当前 codegen 的解析、盲写保护、EDIT 锚点、共享入口保护、路由/导入/导出检查提取成可在临时快照上运行的候选验证步骤，并用现有串行回复做等价性测试，不另造一套宽松协议。主线程按完成顺序收件，在批次屏障后按依赖顺序集成；只在允许写集和被引用源码版本均仍有效时应用。即使写集不重叠，共享接口变化也使候选过期。已声明共享路径的越权块要拒绝并要求单独请求；其他越权路径直接拒绝。总负责 agent 处理请求后，主线程沿用 `generation_batch_check()`、实施证据、状态事件和提交路径。

现有 `whole_app_waves()` 会在每轮落盘后立即运行 `whole_app_wave_gaps()` 并标记生成完成，不能只在外面包一层线程池。并行路径需要独立的候选状态：`planned → running → candidate / blocked_on_shared → integrated_unverified → verified / fallback`。局部源码候选不是已实现需求；共享入口/路由集成后，再运行完成检查和相应验收。失败或冲突的组用最新源码重建 prompt，交回现有串行路径。

### 4. 对照实验与启用门槛

覆盖无并行空间的小任务（如 counter/dice，作为负对照）、多模块任务、共享入口密集任务、环/跨组依赖，以及官方规格与生成规格两类场景。相同任务和配置交替运行串行与 2-worker 版本，记录生成阶段及整次运行的 p50/p90、最终通过数、首次可构建时间、token/成功运行、在途峰值、回退和冲突原因。只有 2-worker 明确获益后再试 3-worker。试验目标是生成阶段墙钟时间可重复下降约 20%，且整次运行也有可见收益；默认开启门槛在基线数据到手后确定。官方验收回归、未结算请求、越权写入、源码快照丢失或明显的 p90/成本恶化都阻止默认开启。

## 主要风险与验证点

- **共享文件冲突：** 路由和入口常由多个需求共同修改；用唯一写入所有者和快照版本检查防止覆盖。
- **接口漂移：** 并行组必须共用应用设计和明确接口；合并后跑跨模块源码/构建检查，必要时做一次集中修复。
- **成本与限流：** 并行可能增加重复上下文、token 与 429；用在途预留和动态降并发控制。
- **尾部延迟：** 若大部分需求依赖前一组或集中改同一文件，继续使用现有 wave，比强制并行更合适。

代码切片按顺序交付：**(1)** 观测指标与只读规划器，先报告哪些任务真的可并行；**(2)** 将现有串行 codegen 的候选解析/校验边界提取出来，做等价验证；**(3)** 加任务包、共享请求与 2-worker 调度，再做配对实验。若第一步显示收益空间不足，后两步不启动。测试重点是依赖/环分组、权限范围、共享块拒绝与单独请求、版本过期、回复拒绝、超时取消后的账本、状态转换和单线程回退。验收信任策略、工具模式与修复策略保持原有行为。

## 实施更新（v19-many）

用户决定默认启用一个主协调流程和最多三个子 agent，因此实现配置以本节为准：`OCTOS_ARC_PARALLEL_CODEGEN=1` 默认开启，`OCTOS_ARC_PARALLEL_CODEGEN_WORKERS=3` 为默认并发上限；设为 `0` 可关闭并行。只有设计中的 `modules` 明确给出 `requirements`、至少两个任务包文件互不重叠、依赖可在组内解决、源码快照能完整引用且预算允许时才实际并发。其余任务沿用顺序 wave/节点生成。当前每次应用生成先执行一批最多三个任务包，剩余节点进入顺序 wave；后续可根据实测增加多批调度。

子 agent 使用私有 Octos 配置、代理、数据目录和工作区，只返回文本；主流程按完成顺序结算模型用量，但在批次屏障后统一处理共享修改请求和局部候选。局部候选必须完全符合独占路径权限；新模块必须实际创建。共享修改只接受单独、带基线 SHA-256 的请求，由主流程生成和写入。写前检查引用源码哈希和路径/符号链接边界，写后运行源码检查和 wave 完成检查；不合格的候选回退到现有顺序流程。运行指标记录准入、候选、共享修改、集成及回退原因。默认并发是产品要求，实际提速仍需按上文对照实验量化。
