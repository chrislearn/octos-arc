# v19-p：并行代码生成探索与实施计划

## 目标与当前判断

目标是缩短从应用设计完成到各需求源码落盘的墙钟时间，同时保持构建、验收结果和总成本可控。并行度应由依赖和文件写入边界决定，不应直接把现有顺序队列改成多线程共享写盘。

当前实现已经有两种并行：`spec_parallel.py` 以私有代理和内核进程并行生成/审核规格，`derived_pipeline.py` 在代码生成期间准备测试。主 `Flow` 线程独占生成文件、状态、快照和账本。代码生成本身仍由 `whole_app_waves()` 顺序处理 wave，或由 `implement_sequential()` 顺序处理节点。每个 wave 会读前一轮生成的源码，可能改共享路由、入口和清单，还会在落盘后做源码检查与必要回滚。因此，代码生成的可并行部分是从同一个稳定快照出发、接口已确定、写入范围互不相交的需求组。

## 行业做法与本项目的取舍

- Codex 用独立任务与 Git worktree 隔离并行修改，保留可审查的 diff；这解决的是并行工作空间与合并边界，不表示同一应用的任意代码块可以无条件并行。[Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)
- Claude Code 的 subagent 适合有界任务与上下文隔离；agent teams 用共享任务表、依赖和消息协调独立任务。官方明确提示：同文件编辑、强顺序依赖会抵消并行收益，任务要有不同的文件所有权。[Claude agent teams](https://code.claude.com/docs/en/agent-teams)、[Claude subagents](https://code.claude.com/docs/en/sub-agents)
- Cursor 的后台代理运行在隔离环境与独立分支，异步提交成果供检查。[Cursor background agents](https://docs.cursor.com/background-agent)

本项目可复用上述共同模式：**先定共享契约，隔离并发生成，单线程验证与集成，遇冲突退回顺序生成**。不直接并行 `Flow`、共享 `output_dir`、工具模式会话或共享代理状态。

## 实施顺序

### 0. 固定基线并量化耗时

在同一提交、输入任务、模型路由、预算和运行环境上记录串行基线。现有 `llm-usage.jsonl`、`flow-metrics.jsonl` 与 `analyze-run.py` 已能提供请求、阶段耗时、token 和生成结果；补齐生成阶段开始/结束、等待、冲突、重试、落盘与检查耗时的事件。记录 p50/p90 墙钟时间、首个可用源码时间、最终通过数、请求/token 数和回滚数。先区分模型等待、输出过长、检查与修复耗时，再决定最有价值的并行点。

### 1. 规划可并行的工作组

沿用需求拓扑顺序、`phase_plan` 和应用设计，形成有限大小的候选组。只有依赖已满足且预测写集不相交的组可同批启动；共享入口、路由、持久化层、包清单和未知写集归主流程串行所有。显式写出每组的输入快照版本、需求 ID、接口契约、允许写入路径与输出上限。无法可靠判定写集时，保持现有顺序 wave。

### 2. 受限并发生成候选补丁

先只覆盖无工具的 codegen 路径，默认关闭实验开关，试运行从 2 个 worker 开始。每个 worker 使用私有代理/内核与冻结源码快照，只返回 FILE/EDIT 候选、使用量和诊断，不触碰共享工作区。复用 `spec_parallel.py` 的有界请求、预留预算与主线程记账思路；遵守全局 token、请求、时间与服务端并发上限。主线程按完成顺序接收候选，避免慢任务拖住无关已完成项；应用结果时仍须满足依赖顺序。

### 3. 单线程集成与冲突回退

主线程验证候选所基于的文件版本、路径所有权和响应完整性，再原子应用、运行现有 `generation_batch_check()`、记录证据并提交。若候选触及共享文件、引用了已过期的版本或检查失败，先根据最新源码重建该组 prompt，按现有串行逻辑重试。禁止并发 worker 直接操作 `Flow` 的 `generation_state`、保护快照、测试目录或共享输出目录。

### 4. 对照实验与启用门槛

用小任务和多模块任务分别做串行/并行配对运行，至少覆盖已有 counter、dice、ticket booking 与复杂基准中的代表样本。先比较 1/2/3 worker；仅当生成阶段 p50 墙钟时间下降至少 25%、通过率不下降、token 成本增幅不超过 25%，且冲突回退低于 10% 时考虑默认启用。若收益只在多模块任务出现，按任务规模与独立组数自适应开启。指标是决策门槛，不是预估收益。

## 主要风险与验证点

- **共享文件冲突：** 路由和入口常由多个需求共同修改；用唯一写入所有者和快照版本检查防止覆盖。
- **接口漂移：** 并行组必须共用应用设计和明确接口；合并后跑跨模块源码/构建检查，必要时做一次集中修复。
- **成本与限流：** 并行可能增加重复上下文、token 与 429；用在途预留和动态降并发控制。
- **尾部延迟：** 若大部分需求依赖前一组或集中改同一文件，继续使用现有 wave，比强制并行更合适。

首个可交付的代码切片应是“规划器 + 只读并发候选 + 串行合并”实验开关，不同时改写工具模式、验收策略和修复流程。
