## 用户问题的复审结论

**慢的主要可见原因是长生成/修复段、上下文恢复、失败验收与重复回归。** 已结束 turn 的累计墙钟分别约 208 和 207 分钟；正式验收调用累计分别约 44 分钟。它们不是严格互斥的全程分解，不能相加后计算“模型占比”，也不能把其中模型等待直接解释为供应商排队。缺 TTFT、完整请求账本与资源采样，暂不下 CPU/网关瓶颈结论。

**切工具并不等于修复完成，多轮也不等于空转。** GitHub 代码搜索由旧功能 39/41 到 40/41 再到 41/41，是有验收支持的有效联合修复；目录浏览的 `verified=True` 后仍 0/1，说明该标志只是尝试验证。工作表排序的第一工具修复由缺菜单推进到单元格结果断言，虽仍 0/5，有局部进展；观察点还没有完成证据。方案正确区分了模式、动作、目标验收和联合验收。

**工具调用 >20 的样本价值不能靠最终节点成功倒推。** 共 12 个已结束 turn、400 次工具、4799 秒；即时目标全绿 2/12（16.7%）。只算修复为 5 个、即时全绿 1/5（20.0%），2145 秒。这些 turn 所在的不同节点后来 8/9 目标通过，不能证明长 turn 必不可少。缺原始模型请求账本，因此“模型请求超过20次”的数量仍未知。方案将工具调用和模型请求分开，保留这个未回答项，避免用错口径给出确定答案。
