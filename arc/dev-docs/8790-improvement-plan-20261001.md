# 8790 运行问题的改进方案与实施复审

依据：[运行调查](8790-live-run-process-review-20261001.md)。目标是修复当前适配器的状态和恢复缺陷，使冻结套件的入口依赖参与调度，并修正已复现的内部断言歧义。此次不修改云端正在运行的任务，不启动付费模型，不将诊断探针当作完整产品通过证明。

## 方案与验收标准

| 项目 | 实施方法 | 验收与保护边界 |
| --- | --- | --- |
| 历史拒绝状态残留 | 节点调用者只读取本次结束时仍未解决的拒绝；历史集合继续用于提供上下文 | 锚点失败后内部纠正成功，不再重复实现；真正未解决的拒绝仍恢复 |
| 重复上下文无恢复出口 | 相同源码重复请求停止读取后，允许一次受限工具编辑；共享原调用剩余时间和请求预算 | 无预算、无代理、明确禁用工具、已有写入时不启动恢复；保护测试和原写入规则 |
| helper 入口依赖遗漏 | 冻结 case-plan 新增 setup_requires，记录实际 helper 闭包；运行时先安排入口能力的实现，再执行依赖它的节点验收 | 原需求与业务断言不变；未实现入口时返回未知并排队，不能判通过；原始冻结套件也可从实际 case/helper 源补足旧元数据 |
| 密码错误断言歧义 | 断言至少一条允许的可见错误提示，保留尾部退出、原密码登录检查；更新配方和审核身份 | 无提示、隐藏提示、无关提示仍失败；一条或两条合法可见提示通过；不是产品完整 E2E |
| 400 包装的传输错误 | 严格识别 proxy_error 与 EOF 等明确传输信息，接入现有最多两次代理尝试 | 普通 400、用量已报告、已收到成功响应或输出时不重试；未知用量继续估算，single_attempt 和截止时间有效 |

## 实施前复审

1. **不能将入口依赖当成“必须先测试通过”。** 搜索用例通过 repo() 检查仓库页，仓库页又通过搜索进入，两者存在有效的准备循环。实施采用依赖优先的实现遍历，并允许循环内节点先构建；验收等待其余入口实现，随后补测。不能用普通拓扑排序硬阻塞循环，也不能把源码写入等同于行为验证。
2. `requires` 表示用例业务契约，`setup_requires` 表示公开入口与准备能力，分开保存。对现有套件不改需求 dependencies；新版元数据通过审核并冻结。仅对验证过身份的内部套件启用入口调度，不影响官方套件或候选测试审批。
3. 历史 refused_paths 还有上下文用途，因此不全局清空。当前尝试状态才用于外层决定是否恢复。
4. 不把 needs_context_repeated 加入普通格式纠正列表反复请求，而是只允许一次工具恢复。所有调用仍受原预算与文件保护约束。
5. 不扩大所有 HTTP 400 的重试，也不把“没有 usage”解释为免费或没有生成。保留未知用量账本。
6. 冻结修订只处理 GitHub 套件；保留工作区原有 Sheet、代理 GLM 等未提交改动。修改前保存相关差异，修改后核对。

本轮不直接机械修补生成应用的 Outlet、Popover 或共享数据模块；这些属于运行产物，当前仓库没有该云端应用的原子完整快照。也不在本轮将修复 bool 接口整体改为枚举：先修复代理错误识别，在现有有界恢复内处理，避免扩散调用接口。

## 验证计划

- 针对性单测：成功纠正、仍有拒绝、工具恢复预算、无写入重试、入口闭包/循环/等待及补测、代理重试负例。
- Playwright 合成 DOM：密码断言正反例；加载所有 GitHub spec，保证用例数和尾部断言保留。
- 审核与冻结：校验 GitHub case-plan、review、manifest、业务模型哈希；运行 Rust 内嵌导出测试验证新增元数据在项目导出中保留。
- 全量 Python 回归；最后逐项复审差异，核对既有未提交改动并更新本文实施结果。

## 实施后复审

已按上表实施。复审中补齐原始需求依赖、tiny/截断探测的入口检查、新模块打包，以及旧验收夹具兼容；保持原预算、未知 verdict 和冻结身份保护。

详见[实施后复审及验证证据](8790-improvement-post-review-20261001.md)。本轮新增测试覆盖恢复成功与负例、准备循环、声明依赖、等待补测、运行协调器排序、代理错误分类、浏览器定位器正反例及 Rust 导出元数据。
