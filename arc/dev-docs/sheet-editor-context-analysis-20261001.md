# Sheet Editor 大文件对生成与上下文的影响

结论：**指定云端任务的 Editor 已经大到影响当前适配器的信息交付方式；集中承担多种功能也会放大修复范围。** 影响可从文件统计、补上下文日志和源码索引实现确认，但没有逐请求 prefill/decode 数据，不能定量归因整场多少分钟是由这个文件造成的。

本次重新打开 [工作表云端任务](https://arc-bench.com/runs/2c6418d39ccd)，读取 File 页展示的 Editor 及两个后端模块，并检查 Stdout。统计来自浏览器 DOM，还原时去掉行号、保留逐行源码；不是下载 ZIP 的逐字节摘要。下载项目时等待60秒超时，没有取得完整云端快照。当前页面返回日志最新为2026-10-01 04:17:35 UTC，显示最近刷新12:32:36北京时间，不声称已读到此后的进展。原先12:24:11的两任务分析仍保留原统计口径。

数据和行号见 [Editor 观察记录](repair-plan-evidence-20261001/sheet-editor-observations.json)。另一次本地v15.3实验用于对照机制，单独标注，不替代云端源码。

## 对生成速度的影响

在当前返回的云端stdout中，按generation-agent.stdout去掉stderr镜像，可见**17次显式codegen写入Editor的事件、11个显式请求补Editor上下文的turn**。这些是可见事件下限，不包含全部native工具写入；“写入”日志不能区分FILE整文件与anchored EDIT，因此不能宣称17次都是整文件重写。

如果某次使用FILE重发现有Editor，需要输出约5.8万字符，再加其他文件；若使用小锚点补丁，输出量可显著缩小，但仍需准确交付相关源码、接口与编辑位置。模型输出通常逐步生成，增加输出量会增加等待；增加输入量也可能增加处理成本，但缓存和供应商实现会影响实际耗时。当前没有云端逐请求token、缓存与首响应账本，不能给出已实测的精确速度倍率。

当前适配器并不是“大文件必定用工具”：`main.py:use_structured_edits`先判断实现波的编辑scope是否超过3文件，超过则返回False；其后才判断12000阈值。于是涉及前端、后端和共享数据的宽scope可能仍走文本FILE/EDIT协议。该分支原本用于避免互相依赖文件被请求上限截断，不能直接删除；需要完整补丁批次、同轮额度和构建恢复机制一起改。

## 对上下文交付的影响

云端筛选在02:28:20请求Editor/后端，02:30:43的context1又请求完整Editor/workbooks，耗时142秒。排序在03:40:40因后端25532字符未引用触发拆分，拆分268秒后通过旧功能检查；03:47:15的重试又请求Editor，用了48秒。可见这条链路的问题是**前后端必需闭包没有稳定交付**，而不只是存在一个大文件。早期很小的时候也有NEEDS_CONTEXT，所以11次请求不能全归给文件变大。

在structured tools路径，`main.py:structured_edit_turn`最多保留32768字符整文件源码；一个58118字符的Editor无法整份留在这个预置区，会被替换成“read current file before editing”。这不是工具读取结果自动截断到32768，也不是模型无法读取Editor；它意味着后续要靠索引、grep、行范围读取补信息，往往增加交互。完整prompt生成还可能先经过全源码闭包检查，所以仅启用structured工具并不会自动绕过早先的容量拒绝。

另一次本地同发行版本实验提供容量对照：

| 本地样本 | 已有prompt | 被遗漏Editor | 加回的最低总量 | 上限 |
| --- | ---: | ---: | ---: | ---: |
| 数据校验重组 | 187858 | 40299 | 228157 | 196608 |
| 排序后端拆分后的重组 | 186874 | 57427 | 244301 | 196608 |

第一次引用Editor、缺后端；重组提升后端与库，却删除先前Editor，然后模型再次索要Editor。两个样本的闭包确实放不下当前预算。见 [校验上下文证据](repair-plan-evidence-20261001/editor-local-validation-context.json) 和 [排序上下文证据](repair-plan-evidence-20261001/editor-local-sort-context.json)。它们证明机制可以发生，不证明指定云端具有完全相同的prompt数值。

本地Editor增长另有实测：初次单元格编辑573行/20089字符，排序接受时1556行/57667字符，最终1986行/74889字符。此处的1986行属于本地应用，**不是云端当前1509行的另一个口径**。

## 大文件被索引替换后，索引又遗漏了什么

`source_index.py:SourceIndex.render`只列前20个symbols、前6个function声明、前20个组件，整份索引再截到5000字符。它匹配普通局部const，所以当前Editor前20项包含match1、row1、activeSheet等局部变量；真正的handleFilterApply、handleClearFilter、isRowVisible都在后面，没有进入前20项。

同时，request摘要只匹配fetch调用，而当前Editor有20处requestJson、0处fetch；筛选/排序API关系不会由这段request提取器交付。函数声明摘要没有覆盖主要的箭头处理函数，也没有函数行范围。大文件从prompt退成索引时，模型恰好失去所需功能的位置和前后端契约提示，更容易额外搜索、读整文件或误诊。

该索引是提示工具，不能当作所有工具请求的唯一信息来源；模型仍可grep、读范围。因此判断是**确定存在信息遗漏、可能增加定位成本**，不是已经量化了多少错误由索引造成。

建议按当前需求/失败证据排序符号，给出函数start/end、路径与版本摘要；保留共享state/回调接口及直接消费者。支持箭头函数和requestJson/fetch，匿名排序回调至少可由API调用位置定位。解析不完整明确标unknown，不能用启发式索引替代编译器或删除必需上下文。

## 集中状态带来的实现风险

当前Editor的`handlePaste`第411行、快捷键粘贴第479行，以及排序第1495行等都会setError；第752行一旦error非空，就只返回alert并卸载整个编辑界面。这是源码可确认的共享错误路径：普通操作拒绝可能变成整个Grid消失，后续用例等待Grid/原值就超时。单元格编辑有独立editError，说明错误隔离只覆盖部分入口。尚未用原云端用例独立重放，所以不把它归为当前所有0/5的已验证唯一根因，也不由Grid消失推断后端数据损坏。

另一个跨文件静态不一致：Editor第1447行始终用第一行的显示值作排序option value，第1485行作为sort_column发出；后端workbooks-worksheets第361—363行在has_header_row=false时期待列字母。无表头且首格为数值10时，UI可能发送10而不是A。修复应明确区分显示标签与稳定列标识，前后端共同约定；不能为了缩短Editor只搬走这段代码却保留不一致。

运行时也有可减少的计算：固定50行×10列，isRowVisible在每个cell里调用，第999行使每行重复10次；内部还查activeSheet和header列。可在行级或按sheet/criteria/cells版本计算一次。但是没有渲染性能测量，不能把500次轻量计算称为这次模型生成数小时的主因。优先级低于上下文交付和错误状态隔离。

## 具体拆分方向

拆分按行为与稳定接口进行，先做表现层提取，再处理共享草稿状态。不要把一个1509行Editor机械分成五个片段后全部重新放入prompt。

| 模块 | 迁移内容 | 必须保持的接口/行为 |
| --- | --- | --- |
| Editor协调层 | 当前workbook/worksheet、模块装配、状态身份 | 选中对象、草稿所属对象与请求版本明确分离 |
| useWorkbookSession | 初始加载、切换、撤销重做、服务端响应应用 | 新响应不覆盖更新的选择；失败保留可用Grid |
| useCellEditing + FormulaBar | 编辑开始/提交/取消、公式栏、单格错误 | 捕获起始worksheet/cell；blur/Enter不重复或错对象提交 |
| WorksheetGrid / GridCell | 网格、行列/单格菜单、RangeSelector连接 | role、accessible name、事件次序、隐藏行行为保持 |
| FilterDialog + useFilters | 筛选UI、条件、独立错误、可见性 | 保留operator语义、清除行为、排序后的重算约定 |
| SortDialog + API适配层 | 排序选项与提交 | 显示标签与列标识分开，表头/无表头协议一致 |
| WorksheetTabs / RenameDialog / DataToolbar | tabs、两个重命名入口、功能菜单 | 原来入口唯一、弹窗关闭/焦点契约一致 |
| csv/range工具与样式 | CSV和坐标纯函数、静态样式 | 动态选中/隐藏样式和导出字节不变 |

ValidationDialog已经存在，优先复用，不再建一个重复的组件。上表是职责边界，不要求一次创建全部模块；Editor协调层150—300行、功能文件不超过约12000字符作为首轮设计目标，是否合理由真实闭包统计决定，不作为机械行数门禁。

第一步可在后续生成的初始骨架预置这些边界，减少每叶子都向Editor追加功能。对现有应用先提取纯呈现组件/静态样式，保持事件和状态所有权；验证通过后再迁移hooks。共享错误入口的行为修复与纯重构分别提交，避免把测试改善全部归给拆文件。

第二步同步修改源码选择/索引：只交付当前功能模块、协调层稳定接口、共享state定义和直接前后端消费者；逐项标记未交付路径。未知动态关系必须按需读取或保留完整闭包。即使拆分，总源量基本不变；如果contract_context仍把Editor所有import递归引用，大文件只是变成同样大的多个文件，无法节省上下文。

第三步保留构建、原始目标和规定旧功能联合验收。另测草稿blur/导航、切换工作表、CSV、粘贴拒绝保持Grid、无表头排序、筛选与排序联动、undo/redo、弹窗焦点。冻结测试不改；补充开发诊断与冻结成绩分开。耗时不足就不做自动重构，不能再次借用节点外的预算。

## 验收与复审结论

单纯行数下降不是成功标准。候选应对相同节点前源码、相同冻结需求/用例、相同模型做配对比较，记录Editor与完整必需闭包字符数、实际请求输入/输出token、全文vs范围读取、FILEvs锚点写入字节、重复NEEDS_CONTEXT、墙钟与联合成功。至少同时比较“只拆文件”“只改交付/索引”“两者一起”，以区分效果；没有缓存账本时只报告实际费用可观察部分。

复审通过的新增方向：预防Editor继续集中职责，修复符号/请求索引，稳定版本化闭包；不批准只把上限调大或盲目自动拆分。当前已确认文件大小及静态契约风险，尚无重构、原云端重放或速度对照结果。新增工作包R11已补入 [整体修复方案](repair-speed-fix-plan-20261001.md)，复审边界见 [复审报告补充](repair-speed-fix-review-20261001.md)。
