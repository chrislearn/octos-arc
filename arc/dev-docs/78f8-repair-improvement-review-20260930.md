## 3. 更新后的具体流程

1. 从当前节点、spec、实际失败和源码索引确定此次范围；字面 React 路由可确认时，完整引用其真实页面组件，同时补上祖先共享约束及相关历史节点的原始合同。
2. 对完整提示计费前检查字符预算。旧合同不截断；文本模式无法交付完整约束时转工具模式读取原文。
3. 模型实际修改应用文件。响应不完整、补丁锚点失败和未获得必要源码时继续使用现有写入保护。
4. 测当前节点，再测受共享改动影响的历史节点。目标绿而旧节点红，继续双方联合修复；历史失败不会因一次省略重复测量而消失。
5. 若候选变得更坏并满足回滚条件，恢复最佳源码。单节点先重新测量恢复后的代码；完整套件同步回对应最佳快照的已测证据。不能继续诊断被拒绝补丁的 DOM 或错误位置。
6. 下一模型回合重新计算源码范围和旧合同；重复失败可切工具模式。轮数、时间、请求与 token 上限仍有效。
7. 当前目标和所有本轮历史复测义务都实测通过后才接受叶测试 verdict。加载失败、预算不足、冻结 oracle 冲突或不完整测量都不能当作成功。
8. 本轮复审再单独核对父级共同条款，必要时外置浏览器检查和续修；叶测试通过不等于父级约束全部通过。这一步当前由本次诊断流程执行，通用的自动生成与覆盖审核仍是后续改进。

## 5. 上下文预算与复审结论

在同一基线测量构造的实际提示词，把全局字符上限 196,608 提升到 393,216，A、B、C、D、E 的提示内容各自完全相同：116,035 / 116,126 / 116,094 / 120,572 / 120,481 字符，均能装下。相关历史合同约 5 KB；D、E 的父级加历史合同约 9 KB。E 实际首轮修复提示为 138,964 字符，也在原预算内；比较实验的 120,481 字符是同一基线构造的实现提示，不与实际修复提示混同。因此本例没有扩大总上下文的必要证据；此前问题来自具体信息交付、错误诊断和回滚后证据过期，更多额度不会自动修好这些问题。没有用字符数推断 tokenizer 的实际上下文容量或费用。

复审已纠正：未来节点不能混入保护集合；单节点 description 提到旧 REQ ID 时不能误认成当前工作；文件范围改变必须重建 owner；巨大 spec 快速返回仍要阻止不完整合同的文本回退；重复动作的假设不能变成 verdict；包的显式文件清单不能漏掉新增 import；中途回滚必须先产生当前源码的新证据；实际页面源码不能依赖文件名猜测，构建配置不应混入浏览器路由树。已有测试桩补上新接口的空默认返回或真实 SourceIndex，没有删除原断言。
