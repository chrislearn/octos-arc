# Worktree 合并复核（2026-10-01）

复核对象：`codex/arc-repair-plan-review` 的三个提交（`05b02cc2`、`805d2c14`、`9085f355`），以及本次发现问题后的补修。主工作区为 `v15`。本次合并不覆盖用于模型基线实验的解压适配器、生成应用和原 `v15.3.zip`。

## 本次复核发现并补修

1. **追加修复记忆会破坏 native 编辑范围。** `bind_edit_scope` 用原提示的 hash 绑定源码路径和失败证据，但 `repair_tool_turn` 先追加记忆，再判断执行器。已有记忆时，未直接引用源码的提示会失去绑定路径，退回完整工具执行器；进入 native 时还可能重复添加记忆。改为使用原提示选择执行器和恢复范围，native 执行器仅添加一次记忆，普通工具路径自行添加。回归使用真实范围绑定及真实 native dispatch，验证索引、目标处理函数和记忆次数。
2. **重构后的验证异常未完整回滚。** 原实现只保护生成和 batch check；fallback build、运行时路由检查和旧功能验收异常会留下新入口和新模块。现在整个验证阶段共用异常回滚，恢复重构前未提交内容并删除该次新增模块。回归分别覆盖 fallback build 和旧功能验收异常。
3. **用例通过数不能证明所有旧 spec 已执行。** 原重构门槛用 `total >= len(proven_specs)` 判断覆盖。两个用例都来自 A 时，也可能放行没有执行 B 的重构。改用既有 `suite_is_measured` 检查完整 spec 身份、结果状态及基础设施错误，再要求全部通过。回归覆盖 A 两用例通过但 B 缺失的情况。

前两项的新增回归在补修前真实失败（三个断言失败），补修后通过。第三项是复核时发现的验收覆盖漏洞，新增失败驱动场景已纳入回归。最终主工作区验证结果见[合并验证证据](repair-merge-evidence-20261001/verification.json)；历史 worktree 的 2275 项结果不代替本次验证。

## 合并采纳的改进

- 每次 `verify_app` 使用独立数据目录，构建、启动与测试共用调用预算；停止服务后清理，避免继承 `ARC_DATA_DIR` 造成假回归。
- 新修复轮不再受上一段 `hard_budget_exhausted` 阻挡；同轮 codegen、纠正、fallback 和续跑共享剩余请求额度。
- 工具 started 只代表尝试，匹配 completed 且明确成功才记命令成功；正式业务验收独立记录源码和范围摘要。
- 同一节点携带必要源码路径，重组提示时读取当前版本；大文件可用范围读取及 native 编辑恢复，不因无法整文件引用就盲目重写。
- 只有通过集合增加或可靠的已完成动作前缀推进才增加修复额度；失败文案、栈行变化不算产品进展。
- 节点时间限制覆盖模型、构建、验收；取消清理所属子进程组；节点结束恢复外层 deadline。
- 后端拆分包含真实入口，子模块放子目录，并校对实际注册路由的数量与顺序；未知 loader 保守延后。
- advisory TOML 与 Python 的末轮默认值统一为 0，并记录实际值来源；配置可以显式启用末轮修复。

主工作区已有源码及 `78f8` 文档逐文件与 worktree 导入基线核对一致；较新的 `v15.3-full-qwen-analysis-20261001.md` 单独备份并恢复，避免用 worktree 中较早的快照覆盖。原未提交状态另保留本地 stash 和字节备份，可恢复。
