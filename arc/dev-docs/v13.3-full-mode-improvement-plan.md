# v13.3 全量测试流程：问题分析与改进方案

复核日期：2026-09-29。基线：`v13` 分支 `b5c672ed`，`OCTOS_ARC_TEST_MODE=full`，`qwen3.7-plus`，reasoning `low`，每次运行预算 7,200 秒。任务为 `hackathon--sheet`；线上失败运行 `9ddcec8029b7` 的 `requirements.yaml` 与本地任务文件字节相同。本文只提出方案，没有修改运行时代码。

## 证据范围与当前结论

1. 首次本地运行 `arc/arc-output/v13-3-sheet-full-20260929` 正常退出，24/24 个实现叶节点都被尝试，应用构建、启动和三个页面的浏览器健康检查通过。但 24/24 个节点的行为测试仍未取得有效判定。`.arc/flow-metrics.jsonl` 记录 `derived_preflight.allowance_seconds=0`、`attempted_nodes=[]`；此时约剩 928 秒。`summary.json` 显示设计阶段 6 次尝试共 882 秒，实现阶段 116 次尝试共 5,170 秒。这些是模型请求耗时之和，不等于端到端运行耗时。
2. 从已生成应用继续运行的全量审核任务 `arc/arc-output/v13-3-sheet-full-review-20260929`，在 2026-09-29 13:38:25 UTC 的汇总快照中仍在运行。该快照的 `review/cases.json` 有 28 个已登记用例：3 个 `approved_behavior`、11 个 `unreviewed`、14 个 `approved_smoke_only`。该续跑复用了首次运行的应用，不代表一次全新运行能在 7,200 秒内得到同样结果；它用于观察审核和失败修复的实际行为。
3. 续跑中 `REQ-2-1-3` 一个已批准测试因 `Worksheet options for Sheet1` 无法定位而失败。独立失败审核引用了需求原句和测试语句，判为应用错误；修正 `WorksheetTabs.jsx` 的 `aria-label` 后，唯一活跃测试通过。`REQ-2-2-2` 的唯一活跃测试在两次代码修复后通过。日志原始 `0/4→1/4`、`0/3→1/3` 包括被隔离的兄弟测试，真实活跃测试分别为 `0/1→1/1`。这证明“一个节点审核通过后即可测试”的代码路径已经存在，也暴露了统计口径问题。
4. 审核模型提出的测试与证据质量仍不稳定。当前 `derived_case_review_decision` 共 16 条：3 条批准、2 条要求修正、11 条因引文校验失败而保持 `unreviewed`。生成阶段截至该快照累计接受 15 个脚本、拒绝 31 个候选提案；后者是提案数而不是唯一场景数。拒绝原因中确有缺少提交后断言、CSV 期望值错误及超出需求的输入。不能把这些错误统一归咎于校验器。

## 建议改动

### P0：在实现预算内提前安排已完成节点的审核与测试

**原因。** `arc/main.py:12540` 先完成全部源码生成，才调用 `review_derived_after_implementation`。后者的 `preflight_derived_specs` 在 `arc/main.py:9064` 按剩余时间扣除最终套件与修复预留；首次运行算出 0 秒。系统保住了交付和最终健康检查，却未产出全量模式所要求的独立行为验证。增加总超时或单纯缩小最终预留都不能保证改进。

**实施方案。** 在源码生成阶段结束一个可构建的叶节点或 wave 后，给已完成节点一个有上限的“生成用例→独立审核→运行活跃用例”机会。先用当前构建检查确认应用可启动；下一轮源码编辑前结束该节点的测试运行并恢复测试造成的工作树变化。全局调度器在开始实现前留出最低一个审核、测试、修复闭环的时间和 token 额度；实现任务不得借用这部分额度。到达保留边界时停止接纳新的实现叶节点，保留可构建的部分成果，并执行已审核用例及最终健康检查。预留时间可能使少数未实现节点延期，应通过相同预算下的代码完成率与行为验证率共同评估，不能只优化其中一项。保留额度应依据本机记录的阶段耗时分布设定上下界，不能硬编码为保证 24 个节点都审核完成。

**安全边界。** 独立审核仍需完整需求引文和测试断言引文；`needs_correction` 只允许一次用例修正，再次独立审核仍判错才标 `invalid`。失败后的测试争议仍走现有双独立审核路径。未审核与无效用例只隔离自身，不阻断其他用例。并行模型请求继续使用 `spec_parallel.py` 的私有代理、预算预留和主线程按序写入；应用构建及共享种子测试保持串行。

**验收。** 相同 7,200 秒预算的全新本地运行应在最终交付前至少记录一个 `approved_behavior` 的实际执行或明确记录由于模型/预算失败无法执行的原因；所有实现节点仍有准确 `implemented_unverified` 或已验证状态，不能把代码生成完成标成测试通过。增加调度单测覆盖 wave 后审核、预算边界、共享文件锁与最终预留。

### P1：把审核“引文格式失败”与“用例内容错误”分开处理

**原因。** `arc/derived_case_review.py:186-226` 对需求引文和测试断言做严格校验，这是必要的。现有 `arc/main.py:8783-8858` 只对 JSON 外壳错误重试。审核模型有时返回 `approved_behavior`，却引述了不存在于用例中的语句，或把点击步骤当成断言，导致 `quote_invalid`、状态仍为 `unreviewed`。例如 `review/audit-3.txt` 把重命名操作列为 `obligation_evidence.test_quote`，未提供该义务的断言；其评语还指出没有核对首页链接，却引用了要求编辑页标题和首页链接同时变化的结果。这是内容可能不完整，不能视为纯粹的引文格式问题。

**实施方案。** 对“模型称通过但引文校验失败”的单个用例增加至多一次只读证据重审。固定原需求、测试块、义务集合及文件哈希，要求重新判断完整 THEN 是否被证明，再从原文返回完整断言语句；若原审查涉及多个义务，可撤回未获证明的义务映射，或将内容判为 `needs_correction`，但不得更改测试代码，也不得把更弱的断言升级为通过。若评语承认某个被引用结果未验证，重审不得继续批准该结果。重审后再次运行全部现有 `review_validation_errors`，任何错误继续保持 `unreviewed`。只有内容被审查判错时才进入原有一次测试修正流程；证据重审不计作“修正测试”。

**缓存与成本。** 保持固定系统提示和共享说明前缀，将单用例、错误码、引文放在末尾；仅对 `quote_invalid` 发起一次小请求，并记录额外耗时、token、缓存命中和恢复批准率。若该恢复率不高，则停止增加重审范围。不要放宽 `test_quote` 必须在代码中、必须包含断言且位于动作后的硬条件。

**验收。** 单测覆盖引文缺失、仅动作引文、GIVEN/WHEN 引文、文件在重审期间变化、一次重审失败和正确断言引文；所有这些情形中错误或旧版本用例均不得进入测试。用同一批审核产物回放，记录恢复的合格用例数与误批准数；误批准必须为零。

### P1：超长 blueprint 审核改为有边界的分片审核

**原因。** 首次运行的 `.arc/design/domain-review.json` 为 `status=unverified, scope=over_limit`；`design_readiness` 将 15 个叶节点列为 blocked。`arc/main.py:4079-4127` 已尝试只保留共享领域字段，但完整需求加该字段仍超过上下文限制，因此根本没有独立审核请求。这个结果不能通过继续提高输出 token 上限解决。

**实施方案。** 保留现有全局 blueprint 为唯一设计源。若整体审核超限，按现有 phase/共享实体的所有权切分输入，每片包含其原始需求、关联领域字段和跨片依赖摘要；逐片独立审查，只允许修改本片拥有的字段。合并时确定性检查所有需求 ID 的覆盖、实体身份/存储归属、命令和路由唯一性、跨片引用及原始设计未被片段外覆写；无法验证的片段保持 `unverified`，不能因部分分片通过而把全局 blueprint 标为通过。对跨片共享实体再做一个小型一致性审查，其结论也需有原始需求佐证。

**验收。** 用本次完整需求回放，所有审核提示均低于 `codegen_context_chars()`；无需求 ID 丢失、无相互矛盾的实体所有者或重复路由；中断任何一个分片应只降低对应范围的 readiness，不触发系统性崩溃。分片输入按稳定顺序序列化，以利前缀缓存。

### P1：生成修复提示中的诊断绑定源码版本

**原因。** 首次运行 `REQ-5-1-1` 的重复 sort 路由被 `arc/main.py:4783-4795` 正确拦截，随后经过较长的结构化修复；但后续模型仍被旧的 `backend/routes/workbooks.js:486` 冲突描述影响，连续请求 `NEEDS_CONTEXT`。现场观察显示该行已经变成 validations 路由。具体成因可能包含 `pending_corrections` 的跨轮存留和旧提示正文，不应未经追踪就断言只有一个来源。

**实施方案。** 诊断对象保存问题类型、涉及路径、路由键及产生时的文件哈希/全应用哈希。每次构建新提示和每次编辑后，先对当前文件重新运行相关确定性检查：冲突已消失则丢弃旧描述；仍存在则重建当前文件位置与片段。`pending_corrections` 中仅保留仍有效的诊断，修改源文件后不复用旧行号。对同一来源版本重复的 `NEEDS_CONTEXT` 设置一次有证据的重新引用，随后回到本地检查或工具编辑，不无限循环。不要清掉仍有效的运行时失败证据。

**验收。** 构造“重复路由被拦截→修复移除→下一节点”的回放，下一提示不得包含旧路由位置；若冲突真实存在则仍阻止写入。记录被丢弃的陈旧诊断数和由此节省的请求数。

### P2：统一活跃测试统计与审核漏斗指标

**原因。** `arc/acceptance.py:1292-1296` 把不准执行的测试在 Playwright 副本中标为 skip；`RunSummary.total` 包括全部发现的测试，原始日志 `0/4` 不能直接读作四个失败。后续代码用 `uncontested_derived_results` 正确过滤，但用户界面与日志可能误读。当前存在 `case_states`、`test_admission` 和局部 `derived-coverage.json`，不足以解释时间是花在需求提取、脚本编译、独立审核还是运行。

**实施方案。** 在日志、metrics、handoff 和 Canvas 状态说明中统一记录 `discovered / approved_active / passed / failed / excluded_unreviewed / excluded_invalid / disputed`，明确区分叶节点“代码完成”“测试审核中”“可运行测试部分通过/失败”“覆盖不足”。测试跳过只影响其所属用例；节点通过须满足其要求的覆盖条件，不能仅凭一个活跃用例通过而宣布全部场景通过。统计以用例标题和当前哈希去重，避免重复执行和已复制的历史 ledger 造成双计。

**验收。** `REQ-2-1-3` 的回放应显示 4 个发现、1 个活跃、3 个隔离，修复后活跃测试 1/1 通过；不得显示为完整节点的 4/4 通过。续跑与首跑的统计必须按各自新产生的 ledger 行分开。

## 性能判断与实施顺序

模型/上游请求是主要耗时来源：续跑截至快照的独立用例审核 8 次尝试合计 837 秒、场景生成审核 15 次尝试合计 1,595 秒、义务独立审核 7 次尝试合计 1,049 秒。它们是尝试耗时之和，存在并行重叠，不能相加当作用户等待时间。审核相关请求的缓存命中率远低于第一次运行的实现请求；私有代理的并行机制已存在，瓶颈不能简单归为“未并行”。代码自身又使全量审核被放到最后、超长 blueprint 审核被跳过，并为无效引文留下整节点等待，因此需要改调度与输入质量。

场景生成提示已经列出允许的字面量，编译器也已有一次针对拒绝原因的修订机会（`scenario_review.py:1036`、`arc/main.py:8442-8488`）。当前 31 个拒绝提案不足以证明应放宽字面量或 CSV 校验；先把拒绝原因按“无效值、错误期望、缺少状态断言、无法由夹具执行”等类别计数，再决定是否需要针对特定类别精简提示或补充可验证的示例。

建议按 P0 调度与 P2 统计、P1 证据重审、P1 blueprint 分片、P1 源码版本诊断的顺序实现。每一步单独回放固定日志/用例，再在相同任务、同一模型和预算下比较：首个活跃行为测试出现时间、已审核场景数、无效/争议误执行数、构建健康、总 token、缓存命中和运行结束时未验证节点数。速度提升幅度目前没有可证明的估计，不应承诺数字。本方案只调整 `full` 的质量与时序，不涉及默认模式的选择，也不改变全量模式的审核准入规则。

复审时工作树另有未提交的 `arc/main.py`、`arc/README.md`、`arc/tests/test_fast_test_mode.py` 改动，将默认模式由基线提交的 `fast` 改为 `full`。这些文件不是本报告所改，也不属于上述两次运行的代码基线；实施时必须先确认采用哪一个默认模式并独立验证，不能把该差异算进方案效果。

## 方案复审

- **证据核对。** 首跑的 0 秒审核窗口来自 `derived_preflight` 指标；续跑的三条批准、十一条引文失败与两个节点修复来自当前 `cases.json`、`flow-metrics.jsonl`、Playwright 报告和源码变更。用例批准与节点全覆盖是不同概念，报告未把 1/1 活跃通过写成节点整体通过。
- **安全核对。** 无一项建议绕过独立审核、降低引文要求或扩大错误用例的执行范围；引用错误重审仍需完整校验，一次测试修正和失败后双审核裁定保留。分片 blueprint 不能将局部审核结果冒充全局通过。
- **时序核对。** 提前测试需要以应用可构建且测试数据已隔离为前提；共享应用写入、构建与 Playwright 不并发。模型文本请求可并行，但每个请求须维持现有私有代理与预算预留，结果在主线程按原顺序写入。
- **限制。** 续跑尚未结束；本报告的用例数和阶段耗时采用 13:38:25 UTC 的保存快照，后续实时值会变化。方案效果仍需实施后相同预算的全新运行验证。线上运行的外部环境差异不能由本地通过推断消失。
