# 派生测试一次制：方案复审与实施复审

日期：2026-09-30。范围：没有官方 spec 时，从需求生成、审核派生测试的 `full` 流程。应用代码修复、官方 spec 与显式 `fast` 模式不在本次变更范围。

## 方案复审

旧版 Sheet 续跑的 51 次测试相关模型请求累计约 5,404 秒请求时间，其中义务提取与复核约 1,802 秒，场景初次提案与重试约 2,498 秒，用例审核约 837 秒，审核后修正约 98 秒，执行失败后的复核约 169 秒。这是历史请求耗时之和，有并发重叠，不是当前版本墙钟。优先减少义务的第二轮完整输出和提案重试，比只缩短最终 spec 文件更可能节省时间。

复审接受“一次提案、一次独立用例审核、拒绝即停”的方向，但保留三个边界：

1. 生成候选仍由确定性 DSL、来源和静态检查拦截；未获批用例不能运行或驱动源码修复。
2. 义务规划可省模型自审，但不能把来源不全的账本宣布为完整；每个未覆盖的原文分句应记为缺口。
3. 已获批用例的运行失败仍走现有独立失败归因。这是运行时应用缺陷/测试缺陷裁定，历史样本只占约 3% 请求时间，删除它会使错误测试有机会驱动业务代码修复。

## 实施

- 简单、单分句的需求和祖先原文机械生成带精确引文的义务；复杂文本最多请求一次模型提取，取消常规第二轮义务自审。模型漏掉的原文分句使该节点保持 `incomplete`。旧双轮算法只保留为 `OCTOS_ARC_OBLIGATION_LEGACY=1` 的回退路径。
- 每个场景最多发送一次提案。移除不可用回复的推理档位重试、结构拒绝后的纠错请求，以及前置审核中的第二遍弱场景回访；单个叶节点有多个场景时，各场景仍各有一次机会。
- 每个候选只参加一次独立审核。移除格式重试、缺失 ID 拆分再审、引文复审和审核后重写/复审；审核请求要求使用程序提供的引文 ID。未批准的候选记录 `review_attempted` 与 `discarded`，保留诊断文本，但不得进入行为执行。最终验收也不重审修改过的用例。
- 已提交的叶节点批次和已排入后台的叶节点不会再由前台重提案。`plan.json` 将无可用回复、无有效脚本分别记为 `unavailable`、`rejected`；交接账本分列候选、获批、废弃和未验证场景。
- 后台队列关闭时只保留已开始的叶节点为“已安排”；还没开始的叶节点释放给前台一次制窗口。已开始但失败的批次仍不重试。
- 用例审核的默认请求数和时间上限按一次制收紧；显式环境上限仍有效。

## 复审结果与限制

来源等价复查：对 Keep、Sheet、GitHub 三份固定 YAML，当前保守的机械义务判定分别是 `0/32`、`0/24`、`0/47` 个叶节点。因此这些真实任务主要节省**义务第二轮复核**，不能把省去两轮义务模型请求当作已实现收益。复杂来源的一次模型提取若漏句，会留下明确 `incomplete`，获批用例仍可作为部分验证运行，但不能证明全场景覆盖。

当前只有固定回复和本地单测，尚无同模型、同路由、同预算的完整在线 A/B。正式验收应同时比较首次 `approved_behavior`、每小时获批并执行的场景、负向分支覆盖、错误批准、应用实现率、最终可启动性、推理与缓存 token。速度提升若以关键场景覆盖骤降为代价，应调整场景优先级及批次大小；不得悄悄恢复对同一候选的循环修正。

复审验证：完整本地单测运行 2,109 个，成功 2,082 个、跳过 27 个；最后的小幅状态修正另以 24 个定向测试复验；`py_compile` 和 `git diff --check` 通过。以上证明流程状态和本地行为，不代表线上模型耗时或质量已经提高。

## 整个未提交工作区的追加复审

本轮覆盖所有来源的未提交代码、测试和文档，追查了相关调用链。范围包括一次制测试规划、后台队列与保护快照、启动修复、生成后的词法检查、快捷键浏览器诊断、追踪汇总及打包。没有回退其他来源的改动。

追加发现并修复以下七类问题，新增定向回放验证对应行为：

| 优先级 | 问题与影响 | 已实施的修正 |
| --- | --- | --- |
| P1 | 启动演练走蓝图修复分支后直接重新测启动，之前的业务验收结果仍保留；源码/构建已变化却可能继续显示通过 | 蓝图修复后清空所有旧验收 verdict，随后仍执行启动复测 |
| P1 | 词法检查把合法 `HTMLTextAreaElement` 判为未定义，同时后端沿用浏览器全局白名单，使非法 `window` 引用漏检；新增生成门会放大误报 | 区分前后端全局对象，补入常见合法 DOM 类型；实际 Babel 检查验证 textarea 构造器通过、后端 window 被拒绝 |
| P2 | 后端词法诊断返回 `routes/auth.js:1`，定向启动修复只识别 backend 前缀或 frontend/src，漏掉真正失败文件并进入宽泛工具修复 | 按磁盘存在性解析后端相对位置，完整引用该文件供定向修改 |
| P2 | 上层提案与用例审核虽然各一次，驱动仍可重发三次，代理还可在传输失败后重发；一次制仍有隐含耗时 | 测试提案、义务提取、用例审核限制为一次上游请求；关闭这些阶段的驱动/代理重试和同请求模型回退；请求结束恢复策略。缺失模型的路由仍删除，使后续新请求能使用可用路由。并行 token 预留同步为一次请求 |
| P2 | `Only owners…`、`Saving fails…`、`cannot…` 等拒绝/限制语句被机械生成器标为 success | 扩大保守判定的限制词与词形范围，这些来源改用一次模型提取；失败继续保持明确 incomplete |
| P2 | 义务账本硬编码到 `derived-tests/`，当真正套件使用避免目录冲突的其他名称时，账本可能写入错误目录 | 新旧义务算法都写入当前 `derived_tests_dir`；固定回放验证不会另建或触碰原目录 |
| P2 | 重建审核账本时不保留 `skipped_with_reason` 和 `unverified_gap`；skip 理由也没有内容哈希，可能丢失已完成决策或复用过期决策 | 原输入不变时保留已有 skip 决策；skip 理由参与版本哈希，理由变化后需要新的审核 |

验证：携带本地已安装 Babel 的完整单测运行 **2,125 个，成功 2,100 个、跳过 25 个**，无失败；最后的请求策略冻结与 skip 账本修正另以 80 个定向测试复验，其中 1 个跳过。Python 编译、两个 CJS 语法检查、打包脚本语法检查和差异空白检查通过。真实 Chromium 集成回放保留了故意制造的原始测试失败，并记录快捷键、焦点标签及无后续 API 写入的诊断。临时目录执行 `ARC_PACK_KERNEL=0` 的原打包脚本，生成 131 项归档并验证完整性；解包到干净目录后核心模块导入成功。没有覆盖工作区现有提交包。

剩余限制：词法白名单和机械复杂度判定仍是保守静态检查，不能证明全部 JavaScript 运行语义或自然语言分支。此次没有新模型在线运行，也没有验证可选嵌入内核的打包模式；既有在线运行报告仍按各自截止时点理解。当前复审未发现其他已复现且未修复的阻断问题，不能将此结论等同于全部业务场景通过。
