## 实施后代码复审发现并修正的问题

1. 新辅助模块最初未进入提交包，隔离解压运行测试发现 import 失败；已加入 `pack.sh`，完整回归包含打包入口验证。
2. 闭包携带组合入口最初会改变下一请求的评分、扩出无关页面并破坏稳定前缀；改为先按本轮证据发现源码，再提升携带必需路径。原有前缀复用和未知目标宽范围测试继续保留。
3. “有任意 drop tool”不能代表 shell 已禁用；实际执行器改按 shell 工具集合是否完整禁用及 no_tools 判断。
4. 回滚到 HEAD 会丢掉此前未提交的新实现。现在恢复重构前文件字节，清除该次新增模块，同时保留之前新建的文件；部分输出及取消路径均有回归。
5. 相同通过数但换掉通过用例不能算质量持平；加入最佳已通过集合保护。重复而不明确的测试身份也不能赚取进展额度。

这些修正针对候选代码自身的缺陷，未把第一轮失败隐藏为“全部一次通过”。历史 v15.3 测试记录没有作为本候选放行依据。

## 验证结果

最后完整回归 **2275项，33项跳过，失败/错误为0，83.463秒**；另启用真实 Playwright/Chromium 的相关回归 **26项全部通过，4.913秒**。具体命令、日志摘要及候选源文件指纹由[验证清单](repair-implementation-evidence-20261001/verification.json)记录。新增24个失败驱动测试覆盖：旧flag、新round；段上限与整轮剩余额度；未完成/失败验证；私有目录和异常清理；节点deadline；实际子进程取消；闭包版本；原生编辑路由；迟到请求身份；路由双注册；部分重构回滚；失败文案与动作前缀；同分通过集合交换；大文件靠后处理函数。没有调用模型来模拟这些确定性流程。

相同重建 GitHub 源码、相同两个冻结 spec 共四用例，在新验证器下分别继承脏目录和空目录，均为 **4/4**，总墙钟分别 **10.693秒**和 **10.994秒**。源应用及原脏目录摘要均保持不变，两个调用获得不同私有目录；证据见[真实浏览器配对结果](repair-implementation-evidence-20261001/paired-verification.json)。旧冻结对照在残留状态下为2/4、79.267秒，空目录为4/4、10.931秒；这支持隔离缺陷的修复，不是整个生成流程的速度对比。

对本地最终 Sheet Editor 的同一份源码做索引对照：74889字符、1986行、28处 requestJson。新索引识别44个可调用声明；筛选/校验/排序证据使 handleFilterApply、handleValidationSave、handleSort 等进入前列，并显示准确起始行和源hash。旧索引被局部 const 占满且不识别 requestJson。详见[索引对照](repair-implementation-evidence-20261001/editor-index-comparison.json)。这是本地快照，与云端1509行的观察分开记录；尚未测得模型请求数下降。

## 当前可采纳结论与后续性能验收

代码候选可用于下一轮受控实验；开发复核不等于正式发布或两个云端应用全绿。下一次使用同一冻结应用/测试、模型配置和资源做基线/候选配对，需要同时比较：目标及旧功能通过率、最终全套、有效编辑比例、未测退出、逻辑 request/实际 attempt、上下文交付及墙钟分位数。保留 GitHub 有效长修复和 Sheet 0/5但动作推进的保护样本。

原冻结观察中 >20 次工具调用共有12个已结束turn、即时目标全绿2个；仅修复为5个、即时全绿1个。不同节点后来8/9通过不能证明长turn必要。候选现在能更明确地关联请求、源码变化与正式验收，但本次没有重跑这12个模型轨迹，因此不能宣称多轮模式普遍无效、全部已修好或某个固定截断最优。
