## 本次发现的现有缺陷与复现

### P1：修复消耗全部节点余量，修改后没有验收窗口

`acceptance_loop` 给 node_repair_turn 传 `min(node_timeout, left)`；包装层只进一步取 `seconds_available`，未减去节点验收和已受影响回归的时间。运行真实例子是剩余 1039 秒、修复 1038 秒，随后验收预算耗尽。全任务 final_phase_reserve 不等于当前节点每轮测量的保留窗口。

本地真实包装层、模拟执行器复现：available=1039，forwarded_repair_seconds=1039，wrapper measurement reserve=0。修复应在**每轮开始**按本节点上次构建/测试耗时和待回归范围估算保留窗口，全部代码生成、上下文恢复和工具续写共用同一个扣减后的 deadline；剩余不足时停止写入并把预算交给测量。不能仅增加超时或请求数。

### P1：上下文容量不足的 needs_context 仍没有实现恢复出口

新恢复条件只匹配 `needs_context_repeated`。`_codegen_attempt` 即使所需文件已在 prompt 中，仍追加一份完整 snapshot；超出上下文容量时退出读取循环，并返回 `needs_context`。当前 node_cycle 只查看 last_codegen_refused，不查看这个 requested-context 状态，可能直接进入测试现有未实现功能。

本地真实 codegen_turn 复现：prompt 已含完整源码，5234 字符、容量 10000；再追加同一源码超过容量，结果 `needs_context`，一次模拟模型调用、0 次工具恢复、0 写入，last_codegen_refused 为空而 last_codegen_context_requested 非空。GitHub 最新 REQ-2-2-3 日志也出现连续需要 App.jsx 的 `needs_context`，不是 `needs_context_repeated`。**未取得云端完整 prompt，不能证明云端正是容量触发；但其状态确实不在新增恢复条件中。**

改进应区分已引用相同版本、未引用的大文件、真正时间/请求耗尽：前两类去重引用或直接给剩余预算内的小范围工具恢复，最后一类停止；不可把所有 needs_context 无条件重试，也不能重新用历史 refused_paths 触发整文件生成。

### P2：跨模块接口问题发现后仍依靠昂贵的浏览器修复

源码中 repair_overwritten_route_exports 有定义但没有调用点。上一轮 CommonJS accounts 导出覆盖已被实际测量证明；本次 teams 的 undefined 又显示跨模块接口需要核对。应让确定性的接口问题在已写入、构建/启动之后进入有界修复队列，携带调用方/导出方完整证据；修复后重新测量。不能静态修完就宣称业务通过。

### P2：Sheet 旧保存失败测试绑定了具体 API

本地 v15.5 内核离线导出的 REQ-3-1-1:25-30 只拦截 `**/api/workbooks/*/worksheets/*` 的 PATCH 且 body.cells 存在，再要求显示指定错误。线上该节点三次为 6/7，失败恰在 line 30；可见生成了 `backend/routes/cells.js`，但尚未取得实际调用 URI，因此“注入未命中”是待确认假设。不能要求模型硬改其 API 来迎合冻结测试。

当前工作区该 spec 已有按同源写请求及唯一失败值注入的修改，属于本轮开始前/并行的现有改动，本次没有覆写；它需要随新内核打包才可能作用于新运行。需要以至少两种 API 形状验证确实注入故障，且缺少错误/未恢复旧值的应用仍失败。
