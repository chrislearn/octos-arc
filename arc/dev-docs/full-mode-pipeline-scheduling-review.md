# Full 模式双队列调度方案与复审

日期：2026-09-29。状态：设计方案，未修改运行时调度。目标是在行为测试生成和审核慢于代码生成时，让实现继续推进，同时确保至少有明确预算和机会执行已审核测试，并维持代码生成的缓存收益。

## 证据与约束

- 当前运行先用 `prepare_derived_tests` 编译机械用例，随后 `prepare_build` 建立应用设计和 phase 计划；源码生成结束后，才调用 `review_derived_after_implementation`。位置：`arc/main.py:12467`、`:12519-12541`。生成中的广域回归检查默认被 `_generation_active` 跳过（`:10941-10948`）。
- 全量测试的一个批次依次进行义务提取、场景脚本提议、独立用例审核、必要时修正和复审，然后更新受保护测试文件；`prepare_derived_spec_batch` 会写 Flow 状态、测试文件、账本和快照，不能直接整体放进后台线程（`:9295-9395`）。
- 现有 `spec_parallel.py` 已能让**无工具模型文本请求**使用私有 proxy/workspace 并预留 token，主线程按序记账和写文件；但 `OrderedSpecRequests.ordered()` 是同步迭代器，取下一个结果或退出上下文都可能等待，不能原样跨越整个代码生成阶段（`arc/spec_parallel.py:1-105`、`arc/main.py:3640-3755`）。
- 7,200 秒 sheet 首跑中，设计请求耗时之和 882 秒，实现请求耗时之和 5,170 秒；实现阶段提供方报告的 prompt cache hit 为 63.9%。24 个实现叶节点都尝试了，但审核窗口为 0 秒，24 个节点都未取得行为判定。续跑的测试生成与审核请求仍慢且有无效引文。数据见 `arc/arc-output/v13-3-full-evidence/summary.json`、`review-summary.json` 与 `arc/dev-docs/v13.3-full-mode-local-run.md`。请求耗时之和可能有重叠，不能当作端到端用时。
- 测试场景以需求、夹具、共享 helper 和义务计划为输入，不依赖当前应用源码；义务只有完成独立复核后才能用于准入。独立用例审核明确不看应用代码（`arc/main.py:8554`）。因此模型文本可以在代码编辑时生成，但测试**执行结论**必须绑定实际运行的源码版本。

## 调度：代码不等测试，验证不等所有测试

建立两个有界队列和一个主线程提交器。实现队列仍按依赖顺序写代码；测试队列在 `prepare_build` 产出稳定的 phase 计划后启动，按 phase/叶节点优先级处理 `义务提取 → 场景提议 → 独立审核 → 必要的单次修正与复审`。两队列共享真实时间和 token 预算。测试 worker 可以在自己的内存/临时目录完成纯函数解析与下一阶段提示构造，但不能写共享工作树、Flow 状态、正式账本或受保护文件。

1. **尽早发出第一批。** 在首个实现 wave/节点前，用冻结的需求、夹具、helper 哈希、phase 计划生成第一个小批次的请求。第一批必须是真实工作，不增加专门的“缓存预热”调用。首批沿用现有约 3 个场景/用例的批量尺度；不把整个需求树塞进一个请求。先覆盖首个依赖链，以及需求明确涉及的认证/基础导航，再轮转其他 phase，避免只产出入口检查。
2. **整条测试链异步，提交非阻塞。** 增加长期存活的 `SpecPipeline`：`submit_batch(snapshot)`、`poll_ready()`、`close(deadline)`。每个不可变 snapshot 带 `phase_id, leaf_ids, requirement_sha, fixture_sha, helper_sha, phase_plan_sha, deadline`。worker 在私有空间依次完成这个小批次的义务提取与复核、场景提议与纯函数编译、独立用例审核及必要的单次修正/复审；每个阶段仍是新的独立模型请求，不向审核器提供应用代码或运行结果。worker 返回原始回复、候选脚本、审核证据、输入哈希和用量，**不直接赋予批准状态**。主线程在代码 turn 前后或 wave 结束时调用 `poll_ready()`，只消费已经完成的批次，重新执行确定性解析、编译、引用/哈希校验，随后写正式文件、审核准入、账本和保护快照。这样即使一个代码 turn 持续很久，测试批次也能在后台走完多阶段，而不止完成第一笔请求。一个慢批次不能让其他独立批次的已完成结果排队；同一叶节点的阶段顺序仍严格保持。共享账本按请求 ID 去重，最终按确定性 key 汇总，而非依赖完成顺序。
3. **代码继续推进。** 若节点 A 代码完成但其测试仍在 `generating/reviewing`，记录 `implemented_unverified`，立即实现可入队的 B。若 A 的测试到 B/C 之后才获批准，在下一个安全检查点运行 A；不回滚到“等 A 审核完再写 B”。任何未审核、无效或仅入口用例都不得进入行为验收和修复。
4. **检查点只运行已就绪子集。** wave 结束、已有应用可构建且确有新增 `approved_behavior` 时，主线程短暂停止代码编辑，提交测试产物。只有目标节点及该用例所需的依赖节点均已实现、构建/启动健康、数据夹具可可靠隔离时，才执行对应节点及受影响的既有回归用例；否则记录 `waiting_for_dependency` 或 `fixture_unreliable`，不把这个执行失败当应用缺陷。测试运行时工作树不能被代码 turn 修改。若没有已批准用例，检查点只记状态并立即继续实现。检查点运行有时间/次数上限；大套件留给末尾。失败只能在独立失败审核确认应用问题后进入修复。测试审核与源码运行可以错位；审核记录绑定需求/用例/helper/夹具哈希，执行记录另绑 `app_source_digest()`，后续代码改变只使相关执行判定待复测，不使独立用例审核自动失效。
5. **收尾不再让新代码无限挤占验证。** 实现入队前按剩余时间检查“最终启动/浏览器健康检查 + 至少一个有界审核/执行窗口 + 已在途任务的记账”。到达边界后停止接纳新的源码节点，已在途文本请求按截止时间收尾；优先运行已经批准的用例，再尝试完成最接近审核通过的批次。没有可运行用例时明确交付 `implemented_unverified` 和具体阶段原因，不能显示通过。当前 `final_phase_due()` 到点后只记录 `continue_generation`（`arc/main.py:10006-10011`），必须改为真正的调度决策；不能仅调大 `preflight_derived_specs` 的时间参数。

慢测试的例子：A 的测试在实现 A 时开始，代码生成先完成 A、B、C；此时 A 的测试才审核通过。代码侧不会在 A 后空等；C 后若有可构建检查点就测 A。B 的测试仍慢则继续留在队列，最后收尾按已批准子集运行。这样改善首个真实反馈时间，不承诺所有节点在固定预算内都验证完。

## 缓存和资源边界

- **代码提示保持原样。** 不把测试队列状态、动态时间、worker 进度或长测试文本插到代码生成提示的前缀。`_generation_active` 期间，`spec_bodies`、`batch_spec_bodies`、`tests_prompt_for` 目前刻意返回稳定的**需求契约**，不读取持续变化的 generated spec（`arc/main.py:5015-5023`、`:5058-5065`、`:5144-5151`）；改造必须保留这条隔离。实现 prompt 的规则、系统消息、工具 schema、源码引用顺序仍保持稳定；仅在已确认失败的修复 turn 附加局部证据。现有按 turn 建会话利用稳定前缀（`arc/main.py:1660-1666`、`:1876-1878`）。
- **测试按提示族连续发送。** 每个阶段固定系统提示和共享说明，把 phase/叶节点/失败细节放在尾部；沿用现有同 phase 批量策略。先完成该提示族的第一笔真实请求，再允许同族最多 2 个并发请求。代码生成期间默认仅允许 **1 个**测试文本请求在途；代码侧空闲、等待构建或进入收尾时可提高至 2 个。并发数是待测的初始上限，不是已证实的最优值。provider 缓存可能按远端路由/模型管理，隔离 proxy 并不能保证互不驱逐。
- **同模型与路由、统一预留。** worker 继承主 proxy 当前路由/模型/推理模式；每进入一个模型阶段时，通过线程安全的中央 `BudgetBroker` 原子预留该阶段的最坏情况 token 和请求数，主代码请求也看见这些预留。不要在批次开始时预留整个多阶段链的上界，以免测试长链把实现请求全部饿死。每阶段结束时 broker **立即**按实际用量（缺 usage 则用保守估计）更新主 proxy 总账并释放预留，不能等主线程结束一个长代码 turn 才结算；正式审计日志可待主线程按请求 ID 落盘。完成、失败、超时、取消都只结算一次。不得让后台 worker 越过总 token、最终健康检查或独立审核预算。保留已有私有 workspace 与 `append_worker_records` 的记账语义，但应扩展为可跨代码阶段存活的生命周期，避免主线程稍后再重复计费；主 proxy 路由发生变化时，未发请求重新取路由，已发请求的结果按原路由记录。
- **缓存验证按阶段，不看全局混合比率。** 记录 provider 返回的 `prompt_cache_hit_tokens / prompt_tokens`、实际未缓存 prompt tokens、请求 p50/p90、按模型/路由/提示族的任务数；实现阶段与原基线单独比较。当前 `prompt_fingerprint` 只与**同一 proxy 的上一请求**比较，私有 worker 每 job 新建 proxy，不能用它的 `prefix_shared_chars` 直接推断跨 worker 缓存命中；新增稳定前缀哈希以查提示变化，最终仍以 provider usage 为准。没有 usage 的请求标 unknown，不能记成零命中。灰度运行以连续窗口观察：若同任务、同模型的实现阶段缓存命中率比串行对照低超过 5 个百分点，或未缓存输入 token 多超过 10%，先暂停代码期测试 worker，只在代码空闲和收尾发请求；这两个阈值是初始回退线，须多次运行确认，不能根据单笔请求切换。

## 预算策略与渐进落地

第一版不额外承诺“每节点必测”。将**现有**最终保留额度分成健康检查、已批准用例执行/一次修复与复测、最后一批测试审核三块，不叠加另一份完整 reserve。具体计算用 `R_health = final_measurement_reserve()`；`R_suite` 按**已批准活跃用例中的优先子集**估算运行时间，并加一次最小修复与复测；`R_tail = min(max(0, 0.25 × 总预算 - R_health - R_suite), max(180 秒, 最近有效审核阶段耗时的 p90))`；新节点入队边界取 `max(现有 final_phase_reserve(), R_health + R_suite + R_tail)`。若近期没有有效审核耗时样本，先用历史同类任务 p90；还没有则用 300 秒冷启动值。若已批准用例多到仅 `R_health + R_suite` 就超出 25%，按依赖与风险选择可执行子集，优先保留实际执行与健康检查，缩小待生成/待审核窗口，不假装能完成全部用例。`R_suite` 不应按未审核 spec 文件数量估算。初始公式须在相同预算的回放中校准，不能宣称是最优参数。若测试队列始终落后，只保留一个优先批次和末尾窗口；不无限积压或同时启动大量模型请求。每一轮在途数、排队时长、各阶段完成/失败数都写入 flow metrics。

实施顺序：

1. 将现有 `prepare_derived_spec_batch` 里的需求/夹具读取、义务校验、场景提议编译和用例审核验证提取为可在私有快照上运行的纯函数；正式审核批准和文件写入仍归主线程。先保留原串行路径作回退。
2. 扩展 `spec_parallel.py` 为长期存活的非阻塞协调器；实现中央预算预留、超时/取消结算、独立批次乱序完成但单节点有序提交。
3. 在 `prepare_build` 后启动测试队列，在 whole-app wave 与 `implement_sequential` 的共同节点完成边界轮询；只在应用稳定的检查点运行已批准子集。不得只改顺序化路径而漏掉 `whole_app_experiment`。
4. 将 `final_phase_due` 变成实际停止新实现任务的边界，同时保留最终构建、启动、浏览器健康检查及全量已批准子集复测。记录真实的 `approved_active/passed/failed/excluded_unreviewed`，避免把跳过的测试算入通过率。
5. 在相同需求、模型、路由、预算下做多次对照运行：比较首次 `approved_behavior` 时间、首次行为测试执行时间、已实现节点数、经完整覆盖验证节点数、全局健康、实现阶段缓存命中率和未缓存 prompt tokens。若代码阶段 p90 明显变慢或缓存命中率持续下降，先把代码期测试 worker 降至 0 或 1，再分析 provider 竞争；不要自动放宽审核。

针对实现增加确定性的调度测试：A 的测试比 A/B/C 的代码慢时 B/C 不等待；长 whole-app turn 中后台能走完一个小批次的多阶段链；B 先于慢 A 完成时 B 可提交但不能越过自己的义务/审核阶段；需求、helper、夹具或 case 哈希在提交前变化时拒绝旧批准；依赖代码未就绪、应用构建失败或测试数据隔离不可靠时不生成应用缺陷结论；取消和超时释放预留且只记账一次；收尾边界同时覆盖 sequential 与 whole-app wave；源代码改变后复测执行结论但保留未变更用例的独立审核。完整运行再验证缓存和分数，单测不能证明远端缓存行为。

## 复审结论与修订

**时序复审。** 原“节点写完立刻测试”的建议不适用于测试生成更慢的实测情况，已修订为“代码不停等 + 已就绪子集在安全检查点执行 + 收尾保留窗口”。单纯把现有 `review_derived_after_implementation` 插入节点循环会阻塞；本方案明确要求拆出非阻塞文本请求和主线程提交。

**长代码 turn 复审。** 若后台只发一笔请求，下一阶段等主线程解析，而主线程正被 1,800 秒的 whole-app turn 占用，那么测试依旧无法在这段时间生成完成。本方案因此让私有 worker 在固定需求快照上完成整个小批次的纯文本/纯函数链；主线程只在安全边界重新验证与提交。这个改动比延长现有 `OrderedSpecRequests` 的线程池寿命更大，必须先把共享状态依赖拆清。

**并发复审。** 整个 Flow 放后台会与代码写工作树、测试文件快照和账本冲突；仅隔离无工具文本请求。Playwright 与共享源码编辑不并发。独立 phase 可乱序完成，但同一节点义务、场景、审核顺序不能颠倒；结果提交必须核对输入哈希，防止旧需求/夹具结果生效。跨节点场景必须等全部实现依赖就绪；若隔离数据或 reset 不可靠，保留未验证状态，不把污染的执行结果用于修复。

**提示输入复审。** 当前实现阶段只给代码模型需求契约。即使后台已产出更多 generated spec，也不能让它们在同一次实现运行中变成新的 prompt 正文；否则提示长度、缓存前缀和测试与代码之间的独立性都会变。只有已审核测试的**实际失败证据**才能进入修复 turn，并继续按现有失败争议流程裁定。

**缓存复审。** “测试生成与代码生成并行”不等于缓存免费。保留稳定代码前缀、同族批量、先单请求后有限并发，并按 provider usage 分阶段测量。若远端缓存仍因并发竞争变差，应降低 worker 数；不能用总体缓存占比掩盖代码阶段退化。

**预算与结论复审。** 固定预算下，早停代码可能降低实现节点数；必须同时比较实现率和经验证覆盖率。即使应用最终健康，也不能推断未执行的业务场景通过。方案尚未实施，首个验证用例出现时间、缓存收益和评测分数均没有可承诺的提升幅度。
