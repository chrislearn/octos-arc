# 参考图视觉预处理：改进报告与复审

复核日期：2026-09-29。范围：ARC-Bench Web 任务在**没有官方可执行测试**时，利用 requirements 中的参考图指导派生测试与应用生成。本文是实施方案及静态复审；尚未接入视觉模型，也没有视觉模型实测、云端分数或成本收益数据。

## 结论

建议增加一次可缓存的视觉预处理，把实际图片转为带来源的候选观察，再分别提供给测试规划、独立审核和代码设计。先做路径解析、证据文件与代码生成提示；只有建立了图片证据的独立审核准入后，才允许图片独有的文字或控件成为派生测试断言。参考图是需求证据，模型解释是可能出错的中间产物；生成测试仍不是官方测试。

## 当前测试生成为什么慢

以下数字取自本地续跑 `arc/arc-output/v13-3-sheet-full-review-20260929` 的已保存文件：请求表 `llm-usage.jsonl` 更新到 2026-09-29 21:59:46、流程指标更新到 21:57:20、用例状态更新到 21:55:33（均为本地时间）。这三个文件不是同一时刻的原子快照。该任务是**已有应用上的续跑**，不能代表一轮全新任务；下面的请求时长是各模型尝试的时长总和，并行请求相互重叠，不能相加当作真实等待时间。

| 阶段 | 已记录尝试 | 时长总和 / 中位数 | 输入字符中位数 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 义务提取 | 8 | 753 秒 / 84 秒 | 7,779 | 其中 2 次上游流未完整结束。 |
| 义务独立审核 | 7 | 1,049 秒 / 193 秒 | 16,049 | 其中 1 次上游流未完整结束。 |
| 场景测试初次生成 | 15 | 1,595 秒 / 102 秒 | 113,396 | 输入包含 DSL、场景目标、阶段上下文和质量规则。 |
| 场景提案重试 | 10 | 1,073 秒 / 106 秒 | 116,756 | 未通过校验的提案再次送入大提示。 |
| 用例独立审核 | 12 | 1,256 秒 / 83 秒 | 61,368 | 审核提示会包含共享 helper 证据，当前长度约 36,649 字符。 |

流程指标记录 7 个 `derived_model_review` 批次、36 个目标槽位、19 个接受脚本与 41 个拒绝提案。目标槽位与脚本、拒绝项不是一一对应，拒绝项还包括重试结果，不应直接算“通过率”。23 条用例审核决策事件中有 12 条因 `quote_invalid` 保持 `unreviewed`；同一用例可被再次审核，事件数不是唯一用例数。保存的 `cases.json` 有 34 条：6 条 `approved_behavior`、16 条 `approved_smoke_only`、10 条 `unreviewed`、2 条 `needs_correction`，不能把 6 条通过视为全需求覆盖。

源码解释了这些数字的主要来源：

1. **全新运行先消耗实现预算。** 首跑 `v13-3-sheet-full-20260929` 的 `derived_preflight.allowance_seconds=0`，最终 24 个叶节点没有可执行的已审核行为测试，尽管结束时还剩约 928 秒。`main.py:12535-12545` 把主要后置审核放在实现之后；是否提前安排测试闭环见已有 `v13.3-full-mode-improvement-plan.md`。单独增加视觉预处理若仍放在这个调度上，可能进一步挤压审核时间。
2. **生成提示大且重复。** `main.py:8285-8337` 每个场景批次重建含同阶段兄弟需求和完整应用设计的上下文；`scenario_review.py:1036` 再加入 DSL 与每个目标的描述、控件、义务等。相同共享信息在初次生成和重试中重复发送。`main.py:8553-8725` 的独立审核每批再带上完整 helper 说明。缓存能缓解部分费用，但不能消除生成输出与审核等待。
3. **两类返工明显。** 多个生成提案缺少动作后的状态断言、重载后断言，或误用不允许的值/CSV 期望，因此被 DSL 拒绝并重试；用例审核还有引文不精确的问题。视觉信息只能帮助确认可见入口与页面状态，不能解决 CSV 精确格式、持久化和引文校验错误。
4. **来源本身有歧义。** 多个错误记录引用需求中的 `the requested workflow` 占位表达；图像或许能指出控件和页面，但若它不能唯一说明流程的动作与结果，应形成覆盖缺口，不能由模型猜出业务规则。
5. **并行已存在，但有边界。** 场景生成、义务提取和独立审核使用 `spec_parallel.py` 的有序请求池；共享 spec 写入与快照保持单线程。单纯“再开更多并发”不一定缩短关键路径，且会争用模型额度、内存及审核预算。

因此速度问题既有请求本身慢，也有**大输入 + 拒绝后重试 + 后置审核预算不足**。参考图若只额外增加视觉调用，没有证据表明总耗时会下降；它必须减少后续无效请求或提高有效覆盖，才能抵消自身成本。

## 如何同时改善覆盖、生成与审核速度

这里区分两种覆盖：**需求行为覆盖**是被已审核且执行过的用例证明的需求分支；**应用代码覆盖**是运行这些用例时实际执行的前后端代码行/分支。当前 `.arc/derived-coverage.json` 侧重场景和用例状态，不能当作前后端代码覆盖率。参考图最多直接改善可见 UI 路径和定位，不能证明后端分支被执行。

| 优先级 | 改动 | 对覆盖的作用 | 对速度的作用与复审边界 |
| --- | --- | --- | --- |
| P0 | 在开始实现前为至少一个可构建批次预留“生成→审核→运行→必要修复”的时间；按完成的 leaf/wave 渐进审核。 | 让已写出的行为测试有机会真正执行；未审核仍不得计入覆盖。 | 避免最后 `allowance_seconds=0`。会占用部分实现预算，须用相同总预算比较，不能只看生成数量。 |
| P0 | 将每个派生目标映射到原需求义务及 `success/rejection/persistence/permission/UI-only` 分类，只补尚无可靠断言的义务。 | 优先补真正缺失的结果分支，避免重复入口 smoke。 | 减少低价值提案和审核项；映射须保留原需求引文，不能由视觉描述独立创造业务义务。 |
| P1 | 生成前读取相关参考图一次，提炼控件名、可见状态、导航层次；同图跨节点复用，摘要只给相关批次。 | 减少找不到入口、把控件位置猜错造成的不可运行测试；可补静态 UI 覆盖。 | 预期减少导航类重试，但要单独计入视觉调用耗时/费用；无图或无价值时跳过。 |
| P1 | 压缩测试生成提示：稳定 DSL 与共享约束放可缓存前缀；阶段上下文只含本批相关需求/设计切片；重试只含失败目标、最小原需求证据与具体校验错误。 | 保留完整需求义务及必要夹具，不因截断漏需求。 | 目标是降低 11 万字符级输入和重复 token；压缩前后做逐目标信息完整性回放，不能只截断尾部。 |
| P1 | 对常见 DSL 错误先做确定性预检查/修正建议，再决定是否花一次完整模型重试。 | 保证仍有状态变化断言、准确字面量及 CSV 格式要求。 | 可避免“缺少动作后断言”等同类错误反复大请求；不能自动把错误期望改成较弱断言。 |
| P1 | 审核输入改为“本用例实际调用的 helper 函数及其传递依赖 + helper 哈希”，保持完整 helper 可查。提供需求/断言的精确引文编号，由模型选编号，程序回填原文并复核语义。 | 审核仍能证明动作与结果，错误引文不会被静默批准。 | 减少每批约 3.7 万字符 helper 证据与 `quote_invalid` 返工；需证明裁剪不会遗漏 helper 副作用或放宽现有审核条件。 |
| P2 | 在成功运行已批准用例时按需收集前后端行/分支覆盖，映射到 leaf、源文件和未覆盖关键分支；只对“需求要求且代码仍未触达”的分支生成下一批候选。 | 使代码覆盖率成为实测指标，能识别未触达的实现分支。 | 插桩、构建和浏览器运行会增加成本，先以少量任务试点；不能为了数字去测试需求外的实现细节。 |

视觉观察可把“点击哪个入口、切换到哪个面板、目标控件在什么状态可见”写成简短导航图，供模型生成 `GIVEN/WHEN` 的可执行路径；真正的 `THEN` 仍由需求原文中的行为、数据和结果支持。对只有图像证据的静态 UI 条件，走前文所述独立图片审核；不要把视觉模型自己生成的“页面应该如何工作”当作测试预言机。

**建议的分阶段实验**：A 仅调整审核预留与批次时序；B 在 A 基础上压缩提示、引文编号与 helper 切片；C 在 B 基础上增加参考图预处理。每阶段在相同任务、文本模型、预算和并发限制下记录首个已审核行为测试出现时间、候选脚本/拒绝/重试、审核请求数、需求行为覆盖、可执行用例通过率、前后端代码覆盖（若开启插桩）、用户等待墙钟时间和额外视觉费用。比较 C 与 B 才能分辨图片是否带来净收益；不应用“生成的测试代码行数”替代覆盖率。

## 建议流程

1. **发现和校验图片。** 沿用需求树提取的引用，保留“图片路径—引用节点—原文片段”的映射。只接受 requirements 目录内的常规本地 PNG/JPEG/WebP/GIF 文件；解析后再次确认实路径仍在目录内，拒绝 `..` 越界与指向目录外的符号链接。相同内容按 SHA-256 去重；远程 URL 记为 `unavailable`，不自动抓取。对不存在、无法解码或超大小限制的图片记录明确缺口。
2. **验证平台调用契约。** 在实际运行环境选一张小图做一次受控请求，确认视觉模型名、base URL、鉴权、`chat/completions` 的图像消息格式、响应格式、超时及计量字段。优先使用平台明确提供的视觉端点与凭据；不要假定文本模型端点可收图，也不要把本地开发密钥写入提交包。未通过探测时走原有文本流程。
3. **生成图像观察。** 对每张唯一图片做一次视觉调用；大图按保持可读文字的方式缩放或分块，并在结果中标明块位置。输入同时给出引用图片的需求原文，要求模型只报告可见事实、位置和不确定项，不补写交互或业务规则。输出经 JSON schema、长度及字段白名单校验，拒绝响应中试图指挥代理执行动作的文本。
4. **保存并关联证据。** 写入 `.arc/visual-evidence.json`，记录需求树哈希、图片相对路径/哈希、模型与提示版本、解析状态、引用节点、观察项、可见文字、位置及不确定项。缓存键至少包含图片哈希、模型名、提示版本和相关需求上下文哈希；evolution 模式只复用键完全一致的观察，过期证据不得静默沿用。
5. **分别消费证据。** 测试规划获取与当前叶节点及其祖先相关的简短观察；应用设计/实现获取相同范围的 UI 结构、状态和素材提示。先保留现有 YAML 字面量规则：视觉观察可以指导步骤顺序、定位策略和样式实现，但图片独有的名称/断言只形成待审核候选，不直接加入 `allowed_literals` 或可信测试集合。
6. **独立审核图片独有断言。** 如果要让某个只见于图片的内容成为可执行行为测试，独立审核必须看到原图、引用该图的需求片段、具体测试断言及图片哈希，确认画面清晰、状态匹配、断言是可观察事实，并再次通过现有测试校验与准入。未通过者可用于代码提示或探索性诊断，不能驱动代码修复或宣布节点通过。

建议先在无官方测试分支启用；有官方测试时只作为设计辅助的后续实验，避免在首版改动中同时改变官方测试流程。视觉请求应有独立的数量、耗时及 token/费用预算；超出预算按被引用节点优先处理并逐张记录 `budget_deferred`，不把未检查的路径描述成已检查。

## 观察数据的最小契约

```json
{
  "schema_version": 1,
  "image": "reference/workbook-home.png",
  "sha256": "<actual image hash>",
  "status": "inspected",
  "requirement_ids": ["<referencing requirement ID>"],
  "observations": [
    {
      "kind": "visible_text | control | layout | state | uncertainty",
      "text": "<short description of visible pixels>",
      "region": "<relative image region or null>",
      "certainty": "clear | uncertain"
    }
  ]
}
```

`status` 还须覆盖 `missing`、`rejected_path`、`unsupported`、`call_failed`、`budget_deferred`。模型的自报 `certainty` 只帮助筛选，不能替代独立审核。证据文件中的文字是外部输入数据，不是新的系统指令；日志不记录凭据、完整请求体或无界 base64。

## 证据准入规则

| 观察来源 | 代码设计/实现 | 派生测试 |
| --- | --- | --- |
| YAML 明确写出的行为、格式、字面量 | 按现有流程使用 | 按现有校验与审核使用 |
| 图片与 YAML 一致的可见布局/控件 | 用于页面结构、样式和入口提示 | 可辅助定位与可见性检查，仍须证明场景动作及结果 |
| 仅图片中可见的文字、控件或静态状态 | 标注图片来源及不确定性后使用 | 先作为候选；原图参与独立审核后才可进入可执行断言 |
| 模型推测的点击结果、校验规则、数据或路由 | 不作为要求 | 不生成可信断言 |
| 图片与 YAML 文字冲突 | 记录冲突，按需求文字实施并保留可见差异 | 不将冲突内容升级为通过条件 |

测试准入继续区分 `approved_behavior`、`approved_smoke_only`、`unreviewed` 等状态；视觉观察不能把“看见入口”变成“行为已验证”。对于没有可验证交互的图片，只能产生静态 UI 检查或未覆盖说明。

## 接入点与实施顺序

**P0：视觉读取器和证据文件。** 新增独立模块，例如 `visual_requirements.py`，处理路径、去重、图像尺寸、调用、响应校验、缓存及指标。`pack.sh` 必须包含新模块。机械派生测试仍可照旧在驱动初始化前建立；视觉调用放在模型代理/驱动就绪后、首批 AI 派生测试规划和应用设计之前。若要更早调用，需显式建立不依赖 `text_turn()` 的客户端，并接入现有请求台账/预算，不能在启动代理前偷发无账本请求。

**P1：只读提示注入。** 为 `scenario_review.build_prompt()` 和应用设计/节点实现提示新增按节点选择的视觉摘要，注明原图路径、证据状态和“不得推断交互”。保留原始需求文本。引用图像较多时按相关性和预算截断，并明确列出被省略的图片。该阶段不扩大派生测试字面量允许集。

**P2：图片独有断言审核。** 给提案增加图片证据引用，扩展校验器与独立审核，使每个新增控件名或静态断言能追到原图和区域；复审验证后才进入 `allowed_literals`/`controls` 的受限名单。用例的前置状态仍须由 YAML 或已验证的步骤建立。不得用视觉模型的同一次文字摘要自我证明。

**P3：图像对照诊断（单独评估）。** 若有必要，再把应用截图与参考图做局部视觉比较，作为样式和布局修复建议；不能直接替代行为验收。此阶段另设阈值和浏览器截图资源预算。

## 验证计划与成功条件

- **离线单测：** 路径越界、符号链接、重复图像、缺图、损坏文件、大图、非图片扩展名、同图多节点引用、缓存失效、模型返回非 JSON/越权指令、视觉预算耗尽；任何失败都能回到现有文本流程并留下状态。
- **提示与准入测试：** 图片证据仅进入相关节点；YAML 字面量校验不被 P1 绕过；图片独有断言在未独立审核时不可执行或指导修复；旧哈希的审核结果失效；图片和 YAML 冲突不改变 YAML 契约。
- **调用契约测试：** 用测试端点校验请求形状、鉴权来源、超时、重试与用量记录；再在实际平台用一张非敏感参考图做一次最小探测，保存去敏的 HTTP 状态和响应结构。当前[公开 Runtime API 文档](https://arc-bench.com/api-doc)未列视觉消息格式，因此真实探测是实现门槛，而不是本文已完成的验证。
- **同预算对照：** 对拥有真实图片且没有官方测试的同一任务，以相同模型、预算和代码版本比较开关前后：被检查/跳过图片数、图片证据进入提示的覆盖率、审核通过的行为用例数、误准入数、首个可执行行为测试出现时间、应用构建健康、最终行为通过率、额外耗时和 token/费用。不要只比较视觉模型主观给出的“相似度”。

首版通过标准：无图/调用失败不影响原流程；每条视觉观察可追溯到实际图片；未审核的图片独有断言不能影响测试 verdict；有图任务在生成前可看到相关视觉证据；开关关闭时产物与现有流程一致。最终分数收益需要真实对照运行后才能判断。

## 复审结果

1. **时序问题：已修正方案。** 原设想“在派生测试生成之前调用视觉模型”若直接插到 `prepare_derived_tests()` 前，会早于代理和驱动初始化。现方案区分机械编译与后续 AI 测试规划，把视觉调用放在两者之间；覆盖首批 AI 规划和代码生成即可满足目的。
2. **测试可信度问题：已修正方案。** 当前 DSL 只接受需求支持的字面量；直接扩大 `allowed_literals` 会让一次可能错误的 OCR 变成测试真值。现方案分 P1 只读建议与 P2 原图独立审核，避免模型输出自证。
3. **输入完整性问题：已修正方案。** 本地任务副本可能仅有引用、无图片；不把“路径存在于 YAML”报告为“图片已检查”。实路径限制也防止图片引用读取 requirements 之外的文件。
4. **成本与调度问题：需实测。** 既有全量测试规划可能被模型耗时挤出预算；视觉预处理必须独立限额、去重并可跳过。尚无平台视觉请求延迟、费用或评分数据，不能承诺净收益。
5. **平台契约问题：待验证。** 截图与历史日志说明可能存在视觉配置；它们不足以证明当前模型、endpoint、鉴权和消息格式兼容。实施前的最小探测不可省略。
6. **性能主因复核。** 续跑请求池已有并行，且许多失败与非视觉义务及精确引文有关。故视觉模型定位为导航/静态 UI 证据补充，性能优化的先后顺序是审核时序、提示裁剪与返工控制，再检验视觉证据的增量贡献。上述秒数是请求尝试总和，不能用作端到端提速承诺。
