# f932fbf5cff1：失败节点回归流程改进方案

日期：2026-10-03。对象：[GitHub 任务运行 f932fbf5cff1](https://arc-bench.com/runs/f932fbf5cff1)，适配器 `arc/main.py`。本文件先固定方案和验收标准，再记录方案及代码复审。当前云端运行不会因本地修改而改变。

## 观察与归因

- 运行有 47 个原子节点；截至 13:50 北京时间处理到第 33 个。日志中的 147 次 Playwright 验收耗时合计约 22,657 秒，49 个修复回合约 8,083 秒。
- `REQ-5-2-2` 在恢复到修改前源码后仍有失败；随后 `REQ-5-2-3`、`REQ-5-3-1` 又分别多次运行约 700 秒、640 秒的历史回归。六次大回归合计约 67 分钟。
- 代码中 `proven_behavior` 是“曾通过”的累积集合；`affected_regression_specs` 把它全部视为当前可保护的绿色行为。`node_cycle` 在节点结束时把 `proven_before` 中所有当前为 `False` 的需求认作这次节点的回归，没有扣除节点开始前已经失败的需求。历史失败因此可能跨节点反复进入回归及恢复对照。
- 目标节点仍失败时，历史回归选集默认最多 16 个 spec。该阶段不能提交目标节点；大范围复测宜留到目标通过后的联合验收、检查点和最终验收。

## 改动

1. 在节点开始时记录已失败的历史需求。节点结束时只有从非失败变为失败的历史需求才进入 `settle_failed_extension`。已失败项保留 `False` verdict，继续进入检查点待办和最终全套，不因新节点重复触发“新回归”的恢复对照。
2. `affected_regression_specs` 的即时选集排除进入当前节点时已明确失败的历史需求；仍保留曾通过集合及其保护契约。目标节点一旦通过，仍测量其余受影响的历史绿色需求。不能把未测、争议或基础设施错误的 `None` 当成已知失败而跳过。
3. 目标仍失败时，每轮历史回归默认上限从 16 降到 4，配置项 `OCTOS_ARC_FAILED_EXTENSION_REGRESSION_SPECS` 保持可覆盖。轮换游标继续工作；目标通过时不使用此上限。
4. 记录被推迟的基线失败；沿用已有 `affected_regression` 指标中的受影响数和实测数，便于下一次运行核对节省的时间及最终覆盖率。

## 约束与验收

- 不能修改冻结的需求或验收用例，不能把未完成的局部测试记作通过。
- 新出现的历史回归仍须按原流程修复或做相同选集、worker 和初始数据的对照测量。已有失败只从即时回归移走，不从最终全套与检查点待办移走。
- 单元测试覆盖：已失败基线不重复对照；本节点新造成的历史失败仍对照；失败目标的默认上限及轮换；目标通过后完整受影响选集仍运行。
- 代码改动后运行相关测试并检查差异；若上述任何保护失效，恢复设计后再交付。

## 方案复审

复审通过，补充三项边界：

1. 只排除**节点开始前**已为 `False` 的需求。若本节点的联合验收首次把旧需求置为 `False`，它仍属于新回归，必须进入修复和对照。不能在每轮按当前 verdict 重新计算排除集。
2. `None` 表示未验证，不能借此次优化跳过。已失败的需求也不能从 `proven_behavior`、检查点 backlog 或最终全套中删除；本改动只改变当前失败节点的即时回归决策。
3. 单用例 60 秒超时可能由冻结用例自身指定；本方案不改原测试超时或断言。缩短即时回归范围只适用于目标仍失败的阶段；接受新实现前继续运行完整受影响选集。

实现时将基线失败集合从 `node_cycle` 传进 `acceptance_loop` 与选集函数，避免读取途中变化的 verdict。配置默认值、README 与测试保持一致。

## 代码复审与验证

复审发现并修复两处实现细节：

1. 最初直接把新参数传给所有 `acceptance_loop` 调用，破坏了替换该方法的旧签名。现在只有确有基线失败时才传新参数；没有基线失败时保持原调用契约。
2. 节点自身可能在重试时已是失败状态；它不是“历史需求”。基线及历史已通过集合均排除当前节点，避免把目标自身记成延后回归。

边界检查：历史绿色集合仍累积保存，`False` 只在当前节点的即时回归选集中排除；`None` 不排除。本节点首次测出的旧需求失败仍进入原有的回归修复/对照路径。失败目标的轮换游标继续前进；目标通过时不启用上限。检查点按预算轮换纳入失败 backlog，最终验收仍受整体时间预算约束。
