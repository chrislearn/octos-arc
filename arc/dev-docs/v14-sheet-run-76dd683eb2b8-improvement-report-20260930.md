## 问题与改进

### P0：停止快照不可启动，现有生成期检查没有形成中断兜底

`workbooks.js` 在校验循环末尾出现 `} HttpError(...)` 和重复花括号。这是确定的语法错误；`backend/server.js` 启动时遍历并 `require` 路由文件，因此该产物会在服务注册阶段失败。产物自带的 `build-check.sh` 只运行前端构建；`smoke-test.sh` 虽尝试启动后端，但没有 `pipefail`，`curl | jq` 不能可靠地把请求失败传成脚本失败。

引擎已有 `generation_checks.check_batch` 的后端 `node --check`，不能简单说“缺少语法检查”。问题是它在写入后运行，并且顺序路径会把错误留给后续修复；取消或进程被强制终止时可能没有下一轮。本次日志没有给出残缺片段的确切写入时刻，不能把它专门归因于 `REQ-5-2-1` 或取消操作。

**实施**：文件协议写入前在临时树解析所有受影响 JS/JSX/JSON；结构化工具编辑在每次原子编辑结束时检查改动文件，失败则保留诊断并恢复该次编辑的前像。写入后仍保留现有批次构建和启动检查，用于捕获导入与运行期错误。每当构建、启动和必要的浏览器健康检查完成，记录可恢复的源码提交及其哈希；优雅终止时检查当前树，坏树恢复最近可启动版本。若平台直接杀进程，依赖持续落盘的恢复点，不能假定终止钩子有运行机会。

**验收**：用本次重复片段做固定回放，坏回复不得成为已提交可交付源码；在编辑中途模拟异常/终止，最终快照要么是经验证的当前树，要么回到可启动恢复点。检查 `build-check.sh` 与 smoke 脚本对后端启动失败返回非零。

### P0：后台候选与公开 spec 脱节，需逐批留下可审计的判定

日志明确把派生测试放在 `/tmp/arc-derived-pipeline-.../derived-tests` 私有目录。运行前版本的 `DerivedSpecPipeline._run` 只在整个 `run_batch` 返回后把结果放入队列；`Flow.poll_background_specs` 才会核对哈希、复制 spec、重建 review 并写 `spec-handoff.json`。该版本任何一次需求树、共享 helper 或本批 spec 哈希不符，都走同一个 `stale_input` 路径并停止后续流水线；`close_background_specs` 以 `close(0)` 立即停止，可能丢在途批次。**这些是可导致结果丢失的代码路径，不是本次零合入的已证实根因**：公开下载包缺失内部指标，无法判定实际命中了哪条路径。

**实施**：每批产生不可变结果包与简短 manifest，记录节点、输入哈希、生成/结构校验/独立审核状态、产出文件哈希、合入结果及拒绝原因。主线程每批单独接纳；局部 spec 冲突只隔离该批，共享需求/helper 变化才使后续冻结输入失效。正常收尾给在途批次有上限的排空；取消时优先持久化已经完成的批次及状态，并保留尚未审核候选的诊断证据，但不把它们标为行为通过。

当前 `b5afd987` 已有局部与共享 stale 分流、按批合并、后台指标转发、暂停/恢复和有上限的 drain；本地工作区还存在未提交修改。下一步应**回放验证这些已有修改**，不要重复实现或用本次旧运行宣称它们生效。

**验收**：用脚本化后台结果模拟三个批次：第 1 批批准并合入、第 2 批只有 spec 冲突、第 3 批有效；最终第 1/3 批可见，第 2 批附具体拒绝原因。再在“模型返回后、主线程 poll 前”和“审核进行中”两个位置中断，确认已完成结果和未完成状态不会无声消失。公开 `spec-handoff`、`review/cases.json` 与内部指标对同一节点的状态一致。

### P1：测试速度与审核效率应按阶段优化

本次最明显的浪费是 CSV 批次：6 个计划场景仅得到 1 个通过生成校验的脚本，12 个提案被拒。第三批也拒绝 8 个提案。只有总数，没有拒绝原因、重试轮数、各阶段模型耗时和缓存 token，无法判断主要耗时来自提示过大、模型输出、编译器约束还是独立审核；直接降低审核标准会把速度问题变成误批准风险。

**实施**：每个场景记录 `planned → requested → response_received → candidate_validated/rejected → reviewed → approved/disputed → committed → executed → passed/failed`，并分别计时。拒绝原因按可操作类别聚合，先对最常见的确定性格式错误做有界修正，重复相同错误时停止空转；保持需求原文、负向分支和独立审核门槛。优先让少量高价值行为路径完成生成、审核和执行的完整闭环，再扩大覆盖，而非用 spec 文件数展示“测试完成”。候选阶段的 `covered` 应改名或另列为 `candidate_coverage`，避免与批准覆盖混用。

**验收**：同一任务、模型、路由、预算的对照运行，比较每阶段墙钟、请求数、推理/输出 token、拒绝类别、`approved_behavior`、实际执行通过数与未验证缺口。误批准保持为零；只报告真实观测到的速度变化。

### P1：第 20 个节点的源码闭包超预算

日志记录 `spec=9897`、`entry=3453`、`room=144752`、`limit=196608`、`required_wave_sources_exceed_budget`。这表明该节点预期需要的源码闭包挤满代码生成上下文；它触发了回退，并不等于模型请求或整个运行失败。应按文件和用途记录预算组成，优先提供目标函数及其依赖、当前错误证据和必要契约；对大共享文件采取安全拆分或两阶段上下文请求。不能裁掉需求必需的源码或凭未声明的模型容量放宽硬门槛。

**验收**：固定第 20 个节点的输入回放，记录裁剪前后实际提供的文件、字符/输入 token、代码生成轮次及构建结果；不能只以“没再报超限”认定改善。

### P2：生成应用的 Z/AA 列边界错误

CSV 导入在 `backend/routes/workbooks.js` 使用 `String.fromCharCode(65 + colIdx)` 生成列名；网格列头和单元格也采用同一方式，并以列名首字符推算最大列。第 27 列会变成 `[`，而不是 `AA`。需求要求保留 CSV 完整行列顺序，这个边界会破坏宽表导入与显示。后端文件已有正确的 `indexToCol`，应复用；前端采用相同的完整列号转换，并用跨 Z/AA 的导入、显示、编辑和导出用例检查。这是本次应用代码缺陷，不应把表格专用规则硬编码进通用生成引擎。
