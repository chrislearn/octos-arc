## 时间与有效产出

观察到约 170 分钟时，两项仍在代码前置测试阶段。电子表格已进入第 5/5 类逐例审核，前四类覆盖记录为 10/44 个规划场景、20/20 叶子 `pending_review`；GitHub 在第 5/6 类义务分析，前四类为 13/51、26/26 叶子 `pending_review`。这两个覆盖分数是审核后的场景覆盖，不是平台得分。

两个在线快照的 `derived-tests/review/obligations.json` 各记录约 1949 秒（约 32.5 分钟）累计义务规划时间，但 `obligations` 均为空；已处理的电子表格 24/24 叶子和 GitHub 26/26 叶子，义务状态均为 `incomplete`。错误包括无效 JSON、`missing inherited source ROOT`、精确引文/适用范围校验不通过，以及模型请求中断。v11.9 的 `obligation_planning.py` 以整批、两轮回复的 `not errors` 作为通过条件；只要仍有结构错误、缺口或未覆盖的父级来源，就不发布该批有效义务。`derived_review_needed` 又把 `obligation_plan_incomplete` 视为验收阻断。因此这 32.5 分钟没有形成可准入的义务账本，也使已经审核过的个别行为用例无法令整叶进入可信测试队列。

## 判断及后续处理重点

原始模型用例的丰富程度较历史显著提高，投入并非完全没有产出；但“约三小时仍没有代码，零叶可进入可信验收”的投入产出比不合理。尤其是义务规划的批次级全有或全无门禁形成了可复现的时间黑洞。当前本地 `v11` 分支已把代码队列放到测试生成之前，这会防止同一问题继续拖延首次写代码，但本地义务规划的审核状态规则仍需另行处理，否则问题会在代码后的测试准入阶段重现。

应优先做有界的小叶义务提取、保留合法的来源引文与逐叶审核状态、把语义争议作为明确缺口而非让整批归零；再核对错误分支、状态不变性、格式精确值与 HTTP 契约是否真正成为可执行断言。以上是在线快照的诊断；本地后续改动见下一节。

## 2026-09-28 后续实施与复核

本地 `v11` 后续修改了 `arc/obligation_planning.py`：默认每批三叶；第一轮只把通过来源引文校验的规范化候选交给第二轮，避免把一整份 2 万多字符的回复再次塞进提示；为每批公平分配截止时间，最长单轮 300 秒；每叶常规最多两次规划尝试，完整性补救窗口可进行第三次。模型现在需明确列出每个叶及每级父级的来源引文，语义缺口须声明影响的叶。即使同批另一叶有错误，合法叶可独立进入 `reviewed`。共享父级条目拆成逐叶稳定 ID，后续重审某叶不会改动兄弟叶已经审核的用例引用。未审核叶仍不能运行派生测试或据此修复业务代码；候选义务及错误继续写入报告。

用下载的旧回复离线重放新解析器，电子表格的 24 个已处理叶中可保留 232 条逐叶候选，但严格校验仅 1 叶达到义务账本准入；GitHub 的 25 个已处理叶可保留 79 条候选，仍无叶达到准入。这个实验说明“逐叶隔离”解决的是整批连坐，**没有证明新提示足以让模型补齐父级约束**。复查发现，纯范围说明的父级不应强求独立的可执行断言；但整段父级文本可能同时包含硬规则，关键词豁免会误放行，故没有采用静态豁免。父级条款需先拆分并审计，才能区分纯范围说明、已有子项细化的概述和必须验收的硬规则。下一轮线上运行应检查每叶的 `errors`、`candidate_obligations`、`attempts`，以及独立审核真正通过的叶数；若仍集中报 `missing inherited source`，需把共享父级契约单独提取、审计，再把其适用范围映射到叶子，不能继续反复生成整批长账本。

下一步的结构性改进应先把原始需求分为带稳定 ID、精确引文的条款清单；再对每条标注适用叶、成功或拒绝分支、可观察结果，以及“纯范围说明/无独立测试义务”的依据。父级条款单独提取和复审一次，硬规则按条件映射到相关叶；不能靠关键词或省略 ROOT 来取消硬要求。叶级测试审核则要逐条核对动作后的断言，特别是状态变化、失败后状态不变、持久化、官方字段与格式、HTTP 状态码。未解决的条款留在缺口账本中，不让业务测试驱动代码修复。时间指标以“经审计且有可执行断言的义务/分钟”为主，并记录超时、无效 JSON、父级遗漏的比例；若新线上数据仍接近零，优先切换到条款级规划而非继续增加整批预算。

本次变更没有重新运行两项在线任务；上述离线重放只验证解析和隔离逻辑，不是新生成质量或最终平台通过率的证据。

## 二审意见核对与修正

- **跨批共享父级义务：意见成立，已修。** 小批量规划时，父级条目的 `applies_to` 可以同时列出本批和其他批次的叶。解析器现在只为本批叶建立经过原文引文和父子归属校验的逐叶记录；批次外叶不会因这条记录获得审核通过，仍须在自己的批次完成审核。只作用于批次外叶的语义缺口也不再否决本批。增加了包含 `ROOT applies_to [A, C]` 的逐叶复现测试。
- **完整性检查缓存：性能观察成立，暂不缓存。** 对 50 叶、每叶两条义务的合成账本连续做 500 次完整性校验耗时约 0.025 秒。需求树和义务列表可原地修改；目前引入缓存需要额外的失效证明，而省下的时间很小。保持每次核对账本原文与稳定 ID，避免旧缓存误放行。
- **最终复测后的启动状态：意见成立，已修。** 最终验收可能再次修复源码。源码变化后，现在还会执行一次不再发起代码修复轮的 build、start、浏览器健康检查；检查结果返回到最终交付判定。失败时沿用已有的最后可启动提交恢复逻辑，恢复成功会清除旧测试结论。
- **纠错复审预算：意见成立，已修。** 240 秒仍是复审上限，同时按 `final_retry_admission()` 保留“验证测量、修复、最终测量”的时间；不足 30 秒即推迟复审，不让复审耗尽最后一次可靠验收机会。

修正后的完整单元测试共 `1888` 项通过，其中 `25` 项因浏览器条件跳过；`py_compile`、工作区及暂存区的 `git diff --check` 均通过。测试证明上述本地边界行为，不能代替新平台运行的通过率测量。
