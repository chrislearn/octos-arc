## 用户提出的四条逻辑流

1. **整体设计/契约/数据模型**先运行。原始 requirements 为权威来源。模型设计成功时保存统一身份、状态、字段、路由和约束；设计失败时使用原始需求及确定性契约继续实现，并记录设计债务，避免整批叶子零产出。
2. **代码生成**只依赖该整体契约和原始需求，不等待生成测试或其审计。生成提示不引用未经审核的派生 Playwright 用例。生成过程中的构建、启动、静态路由/源代码检查仍可发现确定性的系统错误。
3. **测试生成与独立审计**单独推进。初答、编译通过、用例级审核、全叶子义务/场景覆盖分别记录；只有最后一项完成且证据哈希仍有效，叶子才是 `reviewed`。按叶子发布状态到可下载的 `derived-tests/review/spec-handoff.json`。
4. **测试执行与反馈修复**以叶子为准等待审计。未完成审核的叶子标记 `review_pending`，不运行其生成用例，不从其失败推导业务修复、回归、通过/失败判定或最终修复目标。审核完成后立即可以单独测试和修复，无须等其他叶子。测试或 helper 修改使审核哈希失效时，门禁重新关闭。

## 调整与边界

- 原先“首叶测试设计后才开始写代码”的方案仍形成启动依赖，应去除前置调用。单一 driver/proxy、共享文件与受保护测试快照不支持安全的同时写代码和写测试；本次先完成代码队列，再逐叶生成、审核并交接给验收队列，实际 LLM 调用仍串行调度。真正并发需独立进程、会话、不可变契约版本及冲突合并，不在本次引入。
- 系统性错误与业务断言区别对待：构建/启动/确定性运行时错误可由独立健康检查直接修复；生成测试文件自身加载失败应修测试管线；业务断言必须先通过叶子完整审计。不能因为一条用例单独获批就把同叶未审计的其他用例失败用于修复。
- 测试编译与收集是测试审计自身的步骤，可以加载候选文件检查语法；这里的结果不得充当应用验收或业务修复依据。Canvas 是单状态投影，代码已开始后不能再把节点状态倒退为 `designing`；独立的 `spec-handoff.json` 负责展示测试设计/审计状态。
- 官方测试不经过派生测试审计门禁，保持原有执行与修复流程。明确强制整应用生成的旧开关保持原义；默认无官方测试路径采用新交接。
- 未审核并不等于业务通过或失败。最终报告保留所有节点分母，状态为 `unverified/review_pending`；若预算不足，交付代码和未完成审计债务，不编造通过率。

## 实施顺序

1. 将派生代码生成提示统一切换到 requirements 契约；移除代码生成前的派生测试预热/JIT，跳过以候选测试作快速成功判断的路径。
2. 代码完成后运行有界的逐叶测试生成与审计；完成一叶即允许该叶进入本地验收修复，未完成的排队等待。保留最后的完整性补救窗口。
3. 在单叶验收入口、全套修复筛选、波次可选行为检查、跨叶 smoke 与终检选择处统一执行“全叶审计通过”门禁。系统健康检查独立于该门禁。
4. 增加状态与哈希失效、混合已审/未审、预算耗尽、官方测试兼容及生成提示隔离的测试；运行全套回归，复审代码与报告。

## 方案复审

- **没有把测试审计变为代码门禁**：代码阶段只用需求/设计，测试预算耗尽仍写代码。
- **没有把单用例审核误当全叶审核**：复用 `derived_review_needed` 对场景、成功/错误分支、数据格式、义务和源哈希的合取判断。
- **不会用错误测试修代码**：验收入口和任何汇总修复路径均只接收完整审核的叶子；候选测试本身可以供测试审计使用，但不能成为应用失败证据。
- **保留系统修复**：构建/启动检查使用独立证据，和业务用例失败分离。
- **缓存与共享状态**：不启动并发 LLM worker，不让测试文件边写边被代码提示引用；原始需求和设计前缀稳定，受保护快照在每次测试写入后更新。

## 验收条件

- 首个代码生成请求出现在任何派生测试 LLM 审核请求之前。
- 对于同一批次 `reviewed=A, review_pending=B`：A 可以执行/修复，B 的测试不能运行且失败不得进入修复提示或真假 verdict。
- B 审核完成后，不等其他节点即可进入验收；其测试/helper 变动使哈希失效后重新等待。
- 无官方测试的大树最终仍尝试全部代码节点；官方测试路径与独立系统检查保持可用。

## 实施及复审结果

本节在代码实施后补记。当前改动均位于 `v11` 分支，未修改正在运行的两个线上任务。

- `arc/main.py` 先准备全局设计及需求契约，随后执行代码生成队列；派生测试的首叶预热、逐叶生成和独立审核移到代码队列之后。无官方测试时，代码提示使用原始需求编译出的契约，不引用候选 Playwright 断言。单一 driver 保持串行调度；“四路”是独立的状态与交接关系，而非声称同时运行四个模型 worker。
- 代码写完后，先审核首叶，再逐叶审核余下叶子。一叶满足完整义务、场景和逐用例审核且证据哈希有效，就可立刻验收和修复；同批其他叶子仍可待审。默认首轮只准入第一类的第一叶，后续逐叶窗口总额与最终完整性恢复窗口保持分离。超出窗口的叶子保留 `unverified`，不凭候选测试给真假判定。
- `run_specs` 的普通应用验收入口拒绝任何含未完整审核叶子的派生套件；仅测试审计内部可用显式 `audit_candidate=True` 重测候选文件。单叶修复、回归、波次 smoke、阶段集成、全套终检与供应商中断恢复也只选完整审核的叶子。审计修正测试后重新检查哈希，失效即停止应用修复。构建、启动、独立健康检查不依赖派生测试审核。
- `derived-tests/review/spec-handoff.json` 独立记录每叶的 `not_generated/candidate/review_pending/reviewed`、实现状态与测试准入状态；覆盖率/用例纠错刷新该文件。它是可下载的状态快照；实际验收仍实时计算审核状态，不能仅信任 JSON 里的旧值。Canvas 的单节点状态不会在代码开始后倒退到 `designing`。
- 复审另发现 `retain_safe_no_spec_partial` 把派生测试目录当成官方测试，导致已通过确定性构建检查的截断代码被错误丢弃。已允许派生路径保留安全的部分代码；有官方测试、确定性错误或缺失构建检查时仍拒绝保留。

复审中逐一检查了所有 `run_specs` 调用：普通执行均经过中心审核门禁；仅测试审计的纠错重测带 `audit_candidate=True`。外部意见修正后的完整单测共运行 **1876 项，其中 25 项按环境条件跳过，其余通过**。语法编译和 `git diff --check` 无误。

### 剩余边界

- 线上两个任务使用旧 v11.9 包；本分支的新调度尚无平台实测分数。不能以本地单测推断 ARC 通过率。
- 代码优先后，如果实现耗尽总时间或 token，测试审核仍会留下待审叶子；这是明确记录的覆盖债务。下一次线上运行应核对首个代码请求是否先于派生测试 AI 审核、每叶 `reviewed` 数量、审核耗时、进入验收的叶子数与最终分数。
- 当前无并发模型 worker。真正让代码生成和测试审核同时进行，需要分离会话、不可变设计契约及测试文件快照/合并；本轮不引入共享工作区并发写入的风险。

## 缓存命中复核（用户追加要求）

代码中 `OctosDriver` 默认 `OCTOS_SESSION_SCOPE=turn`：每个模型 turn 都是新会话，供应商缓存主要取决于相同模型请求的字节前缀，而非靠跨叶子的会话历史。`app_design_blocks` 把整个设计或稳定的核心/目录放在源代码快照之前，源文件按低变更优先排列；这部分原有的缓存安排没有改。此次新增的代码队列把所有实现请求连续执行，再进入测试队列，避免每叶“测试设计→代码→测试设计→代码”反复切换模型阶段。实现提示引用确定性需求契约，候选测试文件即使在后台改变，也不会改变实现提示里的测试/契约文本；新增单测验证了这一点。

结论：**当前方案没有引入模型并发，也不会因候选测试生成/纠错而破坏实现阶段的共享前缀；代码阶段的请求顺序比旧交错方案更利于缓存。** 不应为了表面并行再开独立模型 worker 或把测试审核插入代码波次。独立测试队列内部仍有不同类型的义务规划、脚本生成、逐例审核和验收修复 turn；这些类型之间的缓存命中不能仅凭静态代码保证。保留逐叶及时验收，暂不因未经测量的缓存担忧恢复整类等待门禁。

线上验证时按生成产物根目录下 `.arc/llm-usage.jsonl` 的 `phase/model/prompt_tokens/prompt_cache_hit_tokens` 分别比较实现、设计和修复阶段命中率，并结合 `prefix_shared_chars` 判断是真实前缀变化还是供应商缓存过期/模型切换；缺 `usage` 的请求不得算作 0 命中。若测试阶段确有可重复的命中率明显下降，再把相邻、同需求大类的少量叶子组成微批次审计，批次结束即释放各个已审核叶子，避免恢复全类屏障。当前没有新包线上运行，不能给出新的实际命中率。

## 第二轮流程与代码复审

按“需求契约 → 连续代码队列 → 独立系统检查 → 逐叶测试生成/审核 → 已审叶验收修复 → 最终复测”的实际入口逐一追踪，补齐了以下边界：

- 代码生成的四条间接提示原来仍可能让模型读取候选测试：节点设计提示、内联设计提示、工具编辑提示及工具回退提示。派生测试模式下已统一要求从原始 requirements、确定性契约和当前源码取证，禁止读取、搜索或运行未审核测试。官方 spec 模式保留原提示。这也避免候选测试变化污染连续代码波次的提示前缀。
- 全套验收在测试审计修正文件并使整叶哈希失效后，现在立即停止该次套件的业务修复；失效叶子的失败不得写入节点测试记录。只通过已审子集时，也不能把全套标为绿色，缺失测试文件的叶子仍列为未验证。
- 受影响回归检查在测量后还会触发测试审计。现在审核失效或有争议的叶子从该次回归结果与修复提示中剔除并保持 `None` verdict；它们不能被标作业务失败，也不会妨碍另一个已审叶子凭自己的有效证据通过。
- 完成代码队列后、耗时较长的测试审核前，先做一次构建、启动与浏览器健康检查；修复轮只使用明确的系统错误。其模型修复调用保留最终复测及修复预算，并且早期检查失败不会回退已生成的整批源码。原有最后一次启动检查继续负责最终交付状态。

由此，“代码可先写”不等于“候选测试可先用于修复”；应用业务 verdict 的依据仍必须满足整叶审计、最新证据哈希和本次测量三个条件。静态代码复审未发现新的无审核候选测试进入普通 `run_specs` 的路径；测试审计内部显式 `audit_candidate=True` 是受限例外。缓存判断仍是静态结构推断，线上真实命中率与通过率有待用新包验证。

## 外部审查意见复核与流程修正

外部审查提出的最终集成验收饥饿问题成立。原先完整性补救借用 `recovery_budget` 时，普通 `final_phase_reserve()` 降至只保留最终测量时间；代码后首叶审核和逐叶审核也只保留测量加一次修复，均可能把跨叶合并测量挤掉。现从候选 spec 数量与 Playwright 单例超时估算套件窗口（最多 900 秒），连同最终测量和修复预算，在整个代码后审核队列及完整性补救前统一预留。窗口不足时继续保留待审债务，优先让已审叶子获得合并测量；最终仍按实际剩余时间选择可负担的已审子集，不能保证所有叶子都在一次套件中运行。

终检纠错后缺乏复审入口也成立。最终派生验收若因测试审计修改文件而使整叶哈希失效，只能得到 `None`，现会对该叶执行**一次有界、只读应用源码的独立用例复审**。只有复审恢复整叶 `reviewed` 状态，才重新运行该叶测试；时间或审核额度不够时继续保持未验证。测试文件或应用源码在终检期间改变后，还会对仍有效的已审子集重新合并测量，避免沿用修改前的证据。最终启动修复若改变源码，也会重新开放一次有预算约束的验收测量；启动修复本身预留这次测量的时间。

其余意见按真实路径核对：

- 派生模式的生产终检走 `final_acceptance_passes` 专用分支；`final_acceptance` 内的整叶失效检查是防御性代码，不是该模式主入口。前文关于“全套验收”的表述应理解为所有验收入口遵守门禁，而非声称派生模式调用了官方 spec 的完整套件修复函数。
- 初始审核窗口优先用于已有实现产出的叶子；实现失败叶子排到完整性补救后段，仍可利用剩余时间补测试。逐叶审核结束后关闭 `node` 会话作用域，避免显式 `OCTOS_SESSION_SCOPE=node` 跨叶混用。
- 派生模式的整页 `rebuild_prompt` 在 `acceptance_loop` 内本来就被禁用；局部失败仍由 `node_repair_turn` 先尝试代码生成再按需转工具。逐叶代码已全部生成后，不能把某叶视为独立的最后一次扩展来运行 `settle_failed_extension`，因为回退节点前提交可能撤销后来节点的实现；保留已有受影响回归检查与最终测量。此取舍是有意的。
- 演进探针在正常 `run()` 中已跳过派生模式；`already_passing_nodes` 的直接调用现在也跳过未审叶子。非派生模式下无效的 `prepare_derived_build_batch` 调用已删除，并把原先断言“代码前生成测试”的失真测试改为断言“代码前不生成派生测试”。
- 提前和最终的启动修复提示在派生模式下明确禁止读取、搜索、运行或修改未审核生成测试。`OCTOS_ARC_DERIVED_FIRST_CODE_SECONDS` 名称保留兼容，当前含义是代码后首叶审核窗口。

以上是本地流程与测试的复核结论，线上通过率及缓存命中率仍需新包运行才能确认。
